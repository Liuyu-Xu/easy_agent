当前修改方向合理：同步、异步共用运行内核；编译、计划数据和工具执行已拆出；普通多输入汇总广播与显式 Hub 端口已实现。工具循环、瞬态错误重试和阻塞线程跟踪也确实存在，旧文档中“完全没有实现”的判断已过时。

## 2. 已复现的实现问题

P1 表示应优先处理的执行正确性或约束绕过；P2 表示契约、数据或诊断不一致；P3 表示较低优先级的维护缺陷。

### OI-048 / P1：兄弟任务活跃时，重试计时器不能唤醒调度器

位置：[graph.py:850](../../../easy_agent/graph.py#L850)、[graph.py:875](../../../easy_agent/graph.py#L875)。探针：`retry_timer`。

循环只在顶部释放到期重试；存在活跃任务时随后无期限等待 `state.completions.get()`。即使并发名额已经空出，到期重试也没有独立唤醒入口。

复现图为一个入口分叉至 A、B，并发上限 2。A 首次失败，计划 10ms 后重试；B 等待 A 第二次执行发出事件，期限 250ms。实际 A 只执行 1 次，B 超时使整图失败。重试本可以在空闲名额中完成。

建议：协调器同时等待任务完成与最近重试到期；任一事件发生后重新释放、调度。计时到期不是业务完成，不应生成提交顺序或占用执行名额；取消和失败仍走统一停止路径。验收必须保留“仍有活跃兄弟任务、且有空闲名额”的反例，现有仅验证快速兄弟任务的测试不够。

### OI-049 / P1：工具续轮按原始上限检查响应，累计预算可被突破

位置：[_api.py:288](../../../easy_agent/_api.py#L288)、[_api.py:299](../../../easy_agent/_api.py#L299)。探针：`cumulative_budget`。

请求确实把剩余 `budget` 发作 `max_tokens`，但响应调用 `_parse_payload(payload, maximum)`，仍用首次总上限校验。末轮直接返回成功，未拒绝累计负余额。

复现：尝试上限 10，工具轮报告用量 7，续轮请求上限 3；最终响应报告用量 6。框架累计已知用量 13，却仍发布成功结果。这里校验的是服务端已报告的用量，不声称客户端可以独立测出真实 Token 消耗。

建议：每轮响应按该轮发送的剩余额度校验，累计账本在工具执行或结果发布前判定；超额不得执行本轮工具或发布成功。维持既定“不同重试尝试独立预算”，不要将它与单次尝试内的工具续轮混为一谈。

### OI-050 / P1：截断或中止的工具响应仍会执行本地函数，日志还改写结束原因

位置：[_api.py:194](../../../easy_agent/_api.py#L194)、[_api.py:295](../../../easy_agent/_api.py#L295)。探针：`finish_reason`。

只要 `message.tool_calls` 非空，解析器就提前返回；`finish_reason` 的正常完成检查只作用于最终文本。受控响应分别使用 `length`、`content_filter`，且携带可解析的参数：两种情况均调用了本地 `add(1,2)`，继续请求并最终成功。

事件还将实际结束原因改记成 `tool_calls`，使诊断记录隐藏了异常结束状态。这是协议完整性与事件真实性问题，不表示已突破工具授权名单。

建议：先校验消息形态与结束原因的合法组合，再允许任何本地工具执行；截断、中止、缺失或不一致的状态应明确失败。事件保留实际经校验的结束原因，不能从消息是否包含工具字段推造。若兼容某类服务端非标准组合，必须显式定稿和测试。

### OI-051 / P2：内部函数工具的 JSON 参数规则弱于 Info、Hub

位置：[_toolcall.py:114](../../../easy_agent/_toolcall.py#L114)；对照 [info.py:40](../../../easy_agent/info.py#L40)、[hub.py:46](../../../easy_agent/hub.py#L46)。探针：`argument_json`。

`json.loads` 默认覆盖重复键并接受 `NaN`。复现中 `{"a":1,"a":9,"b":2}` 实际执行 `add(9,2)`；`{"value":NaN}` 被传入声明为 `float` 的函数，并成功完成。Info 已拒绝非有限浮点数，Hub 已拒绝重复键，内部函数工具却没有相同边界。

建议：用一个严格 JSON 对象解码入口拒绝重复键、非有限数值及非法嵌套值，再进入参数绑定；不要等到工具结果序列化时才发现坏值。复用数据约束，不把 Info 的来源追踪等运行语义强塞给普通参数字典。输入大小上限另属既有 N-3，未在本轮擅自选值。

### OI-052 / P2：函数声明 Schema、Python 签名与执行校验各自解释类型

位置：[_plan.py:42](../../../easy_agent/_plan.py#L42)、[_plan.py:59](../../../easy_agent/_plan.py#L59)、[_toolcall.py:137](../../../easy_agent/_toolcall.py#L137)、[_toolcall.py:164](../../../easy_agent/_toolcall.py#L164)。探针：`parameter_contract`。

| 输入条件 | 模型收到的声明 / 编译行为 | 实际执行行为 |
| --- | --- | --- |
| `value: float`，参数为整数 `1` | JSON Schema `number` | 返回 `invalid_arguments` |
| `value: int \| None = None`，参数为 `null` | 只声明 `integer` | 接受 `None` |
| 同上，参数为 `true` | 只声明 `integer` | 接受 Python `bool`；普通 `int` 参数又会拒绝它 |
| `def positional(value: int, /)` | 校验通过、声明成可调用工具 | 一律用关键字调用，得到 `tool_error` |

这是当前最明确的“相同协议分散实现”问题。编译期解析一次标注，执行时又通过 `get_type_hints`、`inspect.signature` 重建另一套判断；执行期解析失败还会退回空类型规则。

建议：编译时生成冻结的参数契约，Schema 导出、参数绑定和运行时验证共用这一份解释；不支持的签名在发送请求前拒绝。明确 `number` 的整数兼容及 Optional 的 `null` 策略，不能只修一侧；布尔值不得误作整数。尚未选定的新类型或转换规则先登记，不自动扩大支持范围。

### OI-053 / P1：Tool 作为内部工具时跳过其输入和输出 Schema

位置：[_compiler.py:349](../../../easy_agent/_compiler.py#L349)、[_toolcall.py:130](../../../easy_agent/_toolcall.py#L130)；对照 [graph.py:1396](../../../easy_agent/graph.py#L1396)。探针：`tool_object_schema`。

`Tool` 继承 Node，允许配置 `input_schema`、`output_schema`。作为图节点时执行器会验证；作为 `Node(tools=[tool])` 的内部工具时，只包装 `Info(arguments)` 后直接执行 `forward`，不调用这两项校验，声明也只剩泛化 `object`。

复现 `Restricted(input_schema=str, output_schema=int)`：内部调用收到字典并返回字符串，均被接受且整体成功；同一个类作为图节点时，对照探针分别在输入、输出校验处失败。

建议：内部工具的冻结描述符也应携带可执行的数据契约，调用前、后复用相同的 Schema 检查。若某种 Schema 无法映射到本版内部工具的对象参数协议，应在编译期拒绝该组合。不能默默忽略用户已经配置的约束，也不要为此把工具子活动改造成图节点。

### OI-054 / P2：内部阻塞工具超时后，事件错误声称没有运行中的线程

位置：[graph.py:1062](../../../easy_agent/graph.py#L1062)、[graph.py:1105](../../../easy_agent/graph.py#L1105)、[graph.py:1180](../../../easy_agent/graph.py#L1180)。探针：`blocking_timeout_metadata`。

顶层同步 `forward` 按 `execution_id` 登记 Future，内部工具使用独立的 `blocking:<uuid>` 键。超时判断只查前一种键。

受控工具仍在等待线程事件时，框架正确抛出 `NodeTimeoutError` 并保留清理租约，却记录 `deadline_enforced=true`、`blocking_thread_still_running=false`。释放工具后租约才归零。因此现有租约保护并未失效，失真的是超时诊断。

建议：阻塞工作统一关联 run、node execution、attempt；超时查询覆盖该尝试下的全部未结束 Future。保留线程不能强杀的真实语义和现有租约保护，事件应准确反映放弃执行的状态。

### OI-055 / P3：拆分运行状态模块后遗漏 Any 导入

位置：[_runtime.py:8](../../../easy_agent/_runtime.py#L8)、[_runtime.py:20](../../../easy_agent/_runtime.py#L20)。探针：`runtime_type_hints`。

`Info[Any]` 在启用延迟标注后不妨碍普通导入，但 `typing.get_type_hints(_WorkItem)` 实际抛 `NameError: name 'Any' is not defined`。同模块其他相同标注也应一并检查。

建议：补齐导入，并对本轮拆出的模块做一次可解析标注检查。其优先级低于调度和工具约束，不应据此重写运行状态结构。

## 3. 两项一致性问题，不能擅自当成已确定的新功能

### OI-056 / P2：最新文档仍混用历史状态和当前结论

`v0.3-analysis.md` 的模块表已更新到重构后，但正文仍声称同步 forward 在协调器内直接执行、模型完全不能调用工具。`v0.3-open-issues.md` 顶部仍写“本轮未执行测试”，后文又有实际验证与实施更新；OI-001 等条目的现状仍保留旧实现描述。`v0.3-api-minimal.md` 也同时保留“无内部工具、只有一次尝试”的旧范围与后续测试更新。

问题并非历史记录不该保留，而是缺少明确的快照身份和唯一当前状态。按这些文件继续生成修改方案，可能重复实现已经存在的能力。`v0.3-refactor-log.md` 也已说明旧源码行号失效。

建议：保留历史正文并标明版本快照；问题总表给每项维护当前状态、当前函数名和最新验收链接。当前指南、实施结果、历史分析之间的优先级要明确。本轮只登记，未重写这些文件的全部历史结论。

### OI-057 / 待定：max_steps 是否包含内部工具调用，指导和实施口径不同

`v0.3-priority-fixes.md` §3 要求内部工具调用计入现有 `max_steps`、不另设独立步数上限；`v0.3-priority-fixes-log.md` 则描述独立 64 轮上限，源码也确实采用该实现。

探针 `internal_tool_steps` 设置 `max_steps=1`，一次节点尝试内执行了 3 次内部工具和 2 次模型请求，整体成功。当前 `consume_step()` 仅在节点尝试开始调用。这是已确认的行为与文档差异；在确认哪份契约生效前，不断言它必然是调度器缺陷。

建议优先对齐原指导的计数要求，或明确批准“节点尝试步数”与“内部工具轮次”分别计数。无论选择哪种，须解释一轮多工具的计数及上限触发行为，不能继续用一个含混的“总步数”承诺两者。本轮不新增参数、不改计数规则。

## 6. 安全一致性判断

已成立的防线包括账户配置隔离、密钥不进入图导出、HTTP 不跟随重定向、工具名单和权限准入、副作用工具显式拒绝、Info 不可变数据、运行时定义租约、失败后停止投递，以及错误正文的安全分类。本轮正常真实场景的凭据与资源检查通过，现有确定性回归也全部通过。

当前不足主要是同一套防线在不同入口覆盖不完整：

- 文本完成状态严格，工具完成状态宽松（OI-050）。
- Info、Hub 严格处理数据，函数工具参数较宽松（OI-051）。
- 工具向模型声明的参数与本地实际接受的参数不同（OI-052）。
- Tool 作为图节点有 Schema 约束，作为内部工具会跳过（OI-053）。
- 内部线程确实被租约跟踪，超时事件却没有如实反映（OI-054）。
- 请求设置了剩余额度，最终发布却未强制该余额（OI-049）。
