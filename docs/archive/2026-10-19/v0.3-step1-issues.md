## S1-001：有限清理与可终止执行后端未定稿

关联：A03-001、A03-002、P03-003。

原文依据：第一步计划第 6 节要求“不能默认采用修订建议中的 5 秒或以线程冒充可终止 Worker”；v0.3 第 8—9 节要求期限覆盖业务和输出处理，并由可终止 Worker 监督同步业务。

具体缺失：清理参数名称及默认值、Windows Worker 的调用/序列化协议、阻塞 async 和 Schema validator 的隔离选择、终止失败与同步入口退出契约。

本次已完成：绝对期限覆盖输入校验、forward、输出校验和提交检查；吞取消的异步结果无权提交；失败/取消终态在清理前写入；残留资源独立保有 Graph 和共享 Tool 租约；重复外层取消不会提前解冻；已开始的其他 run 不被取消。

仍未完成：主事件循环被同步业务或 validator 阻塞时，不能及时抢占；清理没有有限等待窗口。`arun` 通常等待实际资源退出，重复外层取消可中断这次等待但保留清理租约。同步 `graph(info)` 使用 `asyncio.run`，不合作资源未退出时可能一直等待。拒绝迟到结果不等于调用及时返回。

建议下一步：先正式确定清理窗口和最小进程 Worker 协议，再实现可确认终止/隔离和 Windows 进程测试。未替用户选定秒数、新增 execution 含义或序列化支持范围。

证据：`test_timeout_discards_a_result_from_suppressed_cancellation`、`test_output_validation_shares_attempt_deadline`、`test_repeat_cancellation_retains_cleanup_lease`、`test_synchronous_entry_waits_for_actual_async_cleanup`。同步测试用显式释放的任务验证等待行为，不冒充已实现 Worker。

## S1-002：改变输入数据后的 Info 来源协议未定稿

关联：A03-010、修订建议 D08。

原文依据：第一步计划要求“精确来源类型、别名、重试输入缓存及 Schema 标签规则先核对/定稿”；修订建议第 10 节明确输入派生 `origin_kind` 属于精确协议选择。

具体缺失：输入规范化后新 Info 的 `origin_kind`、producer/parent 字段规则、Schema 标签映射、别名支持范围及重试复用输入的生命周期。

本次已完成：严格 Pydantic 验证结果经过 JSON 模式导出和 Info 数据约束；输出规范化结果进入路由及下游，使用已定义的 `node_output` 来源，validator 只运行一次。改变 JSON 内容时生成新身份和 content_hash；合法原样透传保持原身份。相等判定使用内容哈希，避免 `True == 1`、`1.0 == 1` 掩盖类型变化。

输入边界：验证后 JSON 内容不变时，原 Info 进入 forward；内容改变时，在调用 forward 前抛出 `UnsupportedFeatureError` 并引用本文。没有继续传递错误原值，也没有自行增加 `input_normalized` 等来源类型。此行为是明确阻塞，不能将 A03-010 标为完整修复。

输出支持范围：已验证普通字段、默认值、嵌套 JSON、extra ignore、严格类型及序列化失败；沿用调用者 Schema 标签。未将 D08 的别名政策定为新默认，也不承诺任意自定义 serializer 都能保持接收方 Schema 可往返。

建议下一步：正式定义输入派生 Info 协议与受支持序列化范围，然后将规范化输入传入业务并验证重试缓存。输出规范化无需等待这一决定。

证据：`test_output_schema_normalization_is_published_once`、`test_nested_output_normalization_reaches_route_and_preserves_provenance`、`test_changed_input_is_explicitly_blocked_before_forward`、`test_json_type_change_is_not_mistaken_for_equal_passthrough`。

## S1-003：可重试故障和退避协议未定稿

关联：A03-011、P03-005、P03-006。

原文依据：第一步计划第 6 节说明“0.5/2/8 等仍为建议值，未经定稿不成为公开默认”；v0.3 要求适配器分类的瞬态错误、退避/抖动及外部动作资格共同控制重试。

具体缺失：适配器报告瞬态错误的稳定结构、退避初值/倍数/上限和随机源、Retry-After 解析、Schema 错误开关、外部动作已发生/未知状态及安全重复资格。

当前实现：保留 `max_attempts` 默认 3、严格参数检查及 `retry=n` 到 `n+1` 的兼容换算。框架期限、取消、确定性错误、普通业务及未分类的连接故障均不会自动重试。当前每个逻辑节点实际只开始一次尝试；参数被接受不代表第二、第三次机会已经实现。已删除旧执行器中的不可达重试分支，避免伪造能力。

受控验证：自定义节点抛出 `ConnectionError` 时，即使 `max_attempts=3` 也只调用一次。这证实问题仍受依赖阻塞；没有把所有 ConnectionError 自行认定为可重试。

建议下一步：先审定一个最小适配器故障/动作结果协议及退避配置，再接入协调器的可取消重试队列，验证两次失败第三次成功、名额释放、预算消耗与无重复动作。不要求先接真实模型服务。

可独立继续的工作已完成：停止后禁止成功提交、期限来源区分、实际尝试计入 max_steps、清理期间禁止重新进入，以及不可重试故障只开始一次的验证。

## S1-004：显式 False 的兼容政策保留现状

关联：A03-005、修订建议 D06；不阻塞缺省值修复。

未传 `side_effect` 时，实例继承类及多层继承声明；有效值必须严格为 bool。显式 `False` 保留原有构造行为，不新增“类级 True 不可降低”的政策。`side_effect=True` 的两种放置方式均在业务前拒绝。

如果将来要求 True 为不可降低下限，应先明确修改兼容契约。本文没有把该提案实施为新规则。
