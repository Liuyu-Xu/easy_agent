## 2. 逐项修改

### 2.1 PF-1 阻塞执行

**问题**：同步 `forward` 在协调器内联执行，阻塞期间事件循环冻结，导致兄弟分支被误判超时（实测 0.05s 期限、阻塞 0.5s → 0.536s 才返回；`max_concurrency=2` 时兄弟分支 0.05s 等待实测 0.311s，并在 0.1s 期限下被误判 `NodeTimeoutError`）。

**修改**（`easy_agent/graph.py`）：

1. `_execute_item` 统一为"业务任务 + `asyncio.wait(剩余期限)`"单一路径；同步 `forward` 通过 `ThreadPoolExecutor.submit` + `asyncio.wrap_future` 移出事件循环。
2. 线程池归属单次运行（`_RunState.blocking_pool`，`max_workers = max_concurrency`），运行结束 `shutdown(wait=False)`，不等待被放弃的线程。
3. 期限到达时不再直接取消（避免与清理路径重复取消），改由唯一清理路径处理；`NodeTimedOut` 事件新增 `deadline_enforced` 与 `blocking_thread_still_running`。
4. 新增 `EventLoopBlocked` 看门狗（阈值 100ms，尽力而为，永不使运行失败），记录停滞时长与在途 `node_execution_id`。
5. 定义租约延续：`_retain_cleanup` 从"仅任务集合"扩展为"任务 + 阻塞 future"；future 的 `add_done_callback` 在**线程真正返回**后才释放租约。

**仍有边界**：被放弃的线程会运行到自然结束；进程退出时 Python 仍会 join 该线程。协程内部的阻塞调用无法静态识别，只能由看门狗事后归因。两者都需要 OI-002 的进程 Worker 才能根除，已写入发布说明。

### 2.2 PF-2 重试链路

**问题**：`max_attempts` 默认 3、会校验、会进导出，但 `attempt` 写死为 1，实测只调用一次。

**修改**（`graph.py` + `_api.py` + `errors.py`）：

1. `_execute_item` 支持多尝试：同一 `node_execution_id`，`attempt` 递增；每次尝试独立写 `NodeAttemptStarted`，最终失败写 `NodeFailed` 并附 `attempts_used`。
2. 可重试资格**只由适配器显式标记**：`_api._failure(..., retryable=True)` 给异常打私有标记；`errors._safe_error` 只转发这一个私有属性，不传播第三方文本或其它属性。
3. 判定为可重试：HTTP 408/409/425/429/5xx、传输错误、非框架期限的 HTTP 阶段超时。**不**重试：框架期限超时（立即停整图）、配置/权限/所有权/图校验错误、确定性响应错误、业务函数自身异常。
4. 退避：`Graph._backoff_delay(attempt)`，全抖动 `uniform(0, min(8, 0.5·2^(n-1)))`。返回 `_Retry` 交给协调器的 `state.delayed` 队列，**不占并发名额**；`_release_delayed` 到期后重新入队。
5. 每次尝试独立输出预算（v0.3 §5.4）；`max_steps` 每次尝试计一次。

### 2.3 PF-3 工具循环

**问题**：`Node(tools=[...])` 在编译期被拒绝，模型无法调用任何工具。

**修改**：

1. `_api.validate_model_config` 不再因 `has_tools` 拒绝；模型返回 `tool_calls` 时解析为工具请求（`_parse_payload` / `_tool_calls`）。
2. `call_model` 进入多轮循环：请求 → 若为工具请求则顺序执行 → 回填 `role="tool"` 消息 → 再次请求，直到终态文本。共享父尝试 deadline，**不刷新**；输出预算按轮累计扣减，每轮把剩余额度作为 `max_tokens`。
3. 工具执行走执行器统一边界：`ModelAttempt.tool_runner` 由 `graph.py` 注入，`_run_internal_tool` 复用 `_check_tool_admission`（名称、权限、副作用），产生 `ToolCallStarted/Finished/Failed` 事件，**不**触发图路由与下游投递。
4. 参数严格校验：函数工具按签名检查缺失/多余参数与基础类型，`get_type_hints` 解析 `from __future__ import annotations` 产生的字符串注解；Tool 子类继续以 `Info → Info` 为业务边界。
5. 失败回填而非中断：未知工具名、参数不合法、工具抛异常、结果不可序列化分别回填 `{"error": "unknown_tool" | "invalid_arguments" | "tool_error" | "unserializable_result"}`，异常正文不外泄。**准入失败**（权限、副作用）仍中止尝试。
6. 安全上限：单次尝试内部工具轮次超过 64 轮抛 `ExecutionLimitError`（内部常量，不新增公开参数）。usage 缺失且仍需续轮 → 明确停止，不发布成功。
7. 副作用工具继续在准入阶段拒绝（OI-006 未定稿）。

## 6. 实施中发现的两个环境事实

1. **事件循环时钟分辨率 15.625ms**。`asyncio.wait(timeout=<1 tick)` 可能立即返回，导致低于一个 tick 的期限不可靠。框架自身的期限算术用 `perf_counter`（微秒级），不受影响；但两个使用 0.01s 期限的既有用例必须抬高到 tick 之上。这与历史上的 T13-V01 是同一类问题。
2. **取消只能发一次**。超时分支与清理分支各发一次 `task.cancel()` 会打断节点在 `except CancelledError` 中自行完成的清理。现已统一为单一清理路径，并补了回归（`test_abandoned_blocking_thread_keeps_definition_lease`、既有 `test_synchronous_entry_waits_for_actual_async_cleanup`）。

## 8. 回滚方式

三项互相依赖较少，可分别回退：

1. PF-3：恢复 `_api.validate_model_config` 中的 `has_tools` 拒绝，并把 `call_model` 改回单次请求。
2. PF-2：让 `_execute_item` 只使用 `attempt = 1`，删除 `_Retry` 分发；`_safe_error` 的标记转发可保留（无副作用）。
3. PF-1：把 `_execute_item` 的线程分支改回内联调用，并删除 `_retain_cleanup` 的 future 部分。

回滚后必须重跑：两套 Python 确定性回归 + 联合真实回归（新轮次名与新证据路径）。

## 9. 复核补记（同日第二轮审计）

本文 §1 曾把 PF-3 记为"已实施"。同日复核发现该结论**不成立**：请求体从未声明 `tools`，真实模型不可能返回工具调用，PF-3 只在 mock 下有效。同轮另发现两处缺陷并一并修复，详见 [缺陷复核（第二轮）](v0.3-defect-audit-2.md)。

| 编号 | 缺陷 | 修复 |
| --- | --- | --- |
| D-1 | 工具未声明给提供商 | 新增 `_json_schema`/`_function_parameters`/`_function_spec`，`_ToolDescriptor.spec` 进入请求体；无法导出 Schema 的注解在编译期拒绝 |
| D-2 | `Tool.forward` 兼容桥内联同步 `invoke`，仍冻结事件循环 | 改为提交线程（兄弟分支 0.354s → 0.054s） |
| D-3 | 该线程逃逸定义租约 | 新增 `easy_agent/_blocking.py`，ContextVar 绑定当前尝试的线程池与登记函数，future 计入 `state.blocking_futures` 并自移除 |

**修正后的验证**：确定性回归 **228 项 × 两套 Python**（原记 223）；联合真实回归 19/19；另有一次**专属真实工具探针** 2 次请求验证线上格式与工具执行（输出 `5`，工具实参 `(2, 3)`）。本轮真实请求合计 **21 次**。

**修正后的范围**：PF-3 现在是"真实可用的最小工具循环"，不再只是 mock 通过；副作用工具、审批与账本仍属 OI-006。
