## 2. 共同设计及参考边界

### 2.1 框架职责

| 内部职责 | 保存内容 | 权限边界 |
| --- | --- | --- |
| 定义与编辑事务 | 节点、拓扑、配置、工具声明、定义版本 | 运行和清理租约存在时禁止编辑 |
| 不可变执行计划 | 验证过的拓扑、有效配置、工具描述 | 准入、执行和日志读取同一份计划 |
| 运行协调器 | 运行终态、完成事件、投递、资源归属 | 唯一有权提交正式输出和推进会话的主体 |
| 尝试状态 | 逻辑执行 ID、attempt、deadline、预算、局部消息 | 单次尝试独立；内部工具复用父尝试约束 |
| 会话状态 | 来源列表、接收游标、提交游标、待处理输入、成功历史 | 按运行、接收节点和分组隔离 |
| 后端与适配器 | 实际调用、候选结果、故障分类、usage | 不能直接投递下游或解除定义冻结 |

PyTorch 的模块调用入口与 forward 扩展入口分离，可作为统一包装调用的参考；LangGraph Pregel 的计划、执行、更新阶段可作为候选结果与正式状态分离的参考。本项目继续采用自己的 Info 调度语义，不据此切换成 Pregel 的整批 superstep 调度。[PyTorch Modules](https://docs.pytorch.org/docs/2.14/notes/modules.html)、[LangGraph Runtime](https://docs.langchain.com/oss/python/langgraph/pregel)

### 2.2 共同不变量

1. 运行结果只能从 RUNNING 进入 SUCCEEDED、FAILED 或 CANCELLED，一次运行只有一个终态。
2. 清理状态独立于结果状态；终态可观察不意味着共享定义已经可以编辑。
3. 业务和 Worker 只生成候选结果；正式结果、历史和后续动作由协调器提交。
4. 提交前检查运行状态、尝试身份、绝对期限、Schema 和预算；检查与内存状态提交之间不可 await。
5. 已提交结果不因下游排队而重新计算上游 timeout；尚未执行的投递仍受运行停止状态约束。
6. 修改资格检查、候选定义校验和最终安装与运行租约取得使用同一套同步机制。
7. 工具的放置方式不改变准入；内部调用不重新领取 Graph 执行名额、尝试次数或输出预算。
8. 接收游标与成功提交游标分离；失败尝试不能改变下一轮可见的成功历史。

记录事件应与对应内存状态变化保持顺序。临界区不进行阻塞日志写入或用户回调；必要日志失败沿用既有失败规则，不能因日志异常释放仍需要的租约，或把已失败运行恢复成功。

## 3. A03 问题逐项修订

### 3.1 A03-001：期限未覆盖成功提交

**既有契约**：v0.3 第 8 节、T11—T12。任何一次框架 deadline 到期即停止本次整图，迟到结果无效。

**修改位置**：[graph.py](../../../easy_agent/graph.py) 的尝试执行、结果规范化和正式提交路径；后续执行后端共享同一约束。

**根因**：以 wait_for 的返回或异常代表期限结论，且输出校验不受完整尝试边界监督。

**建议方法**：

- 取得执行名额、开始尝试时保存单调时钟 deadline；排队、等待输入及重试退避不消耗下一次尝试期限。
- 输入校验、业务执行、模型及内部工具续轮、输出校验与序列化均在本次尝试中进行；任何续轮不刷新期限。
- 监督器到期后先使运行 FAILED、使尝试失效并关闭提交及投递入口，再取消任务或终止 Worker。
- 完成通知仅携带候选结果。协调器处理时再次检查期限；入队时未到期不等于处理时仍可提交。
- 提交成功时结束该 attempt 的计时生命周期，并同时登记后续投递或会话推进，避免半完成状态。
- 业务 TimeoutError 保留业务来源，不以异常名称判断框架期限。

**边界**：单调时钟后验检查只能阻止迟到提交，无法中断阻塞事件循环的函数。阻塞业务及校验器必须纳入可终止隔离后端，或明确拒绝不满足后端协议的对象。不能用 to_thread 宣称可强制终止任意同步函数。Python 文档明确取消依赖协程响应，wait_for 的实际等待可能超过 timeout。[Python asyncio](https://docs.python.org/3.10/library/asyncio-task.html)

**验收 R03-01**：吞取消后返回、输出校验超期、临界时刻竞争均无迟到成功、历史或下游调用；业务 TimeoutError 不被改判；已成功提交后下游排队不使上游超时。

### 3.2 A03-002：清理与终态耦合，新运行未被拒绝

**既有契约**：第 4、8 节，T13—T14。

**修改位置**：Graph 运行入口、run 资源集合、退出清理及日志终态路径。

**建议方法**：

- 结果域为 RUNNING → SUCCEEDED / FAILED / CANCELLED；资源域为 ACTIVE → CLEANING → CLEANED，超出窗口仍有资源时记录 CLEANUP_PENDING，之后仍可转为 CLEANED。
- 先使停止终态可观察，再等待清理；不能以任务未退出为由维持 RUNNING。
- 用独立清理租约保护仍能访问定义的残留任务。存在清理租约时拒绝同一 Graph 新运行及编辑；已经开始的其他 run 不被连带取消。
- 维护本次运行的任务、内部调用、退避计时器、IPC 和 Worker 清单。资源确认退出或被验证隔离后才释放对应租约。
- 取消、超时、正常结束及异常路径都执行幂等清理；重复取消不能让资源记录丢失。

**后端约束**：当前同步入口使用 asyncio.run。把残留协程放到后台后返回 arun，不能保证同步入口返回，因为事件循环退出清理仍可能等待它。有限清理需与隔离后端及同步入口生命周期一起验收；再套 wait_for(gather(...)) 不足以解决不合作取消。

**新增提案**：清理窗口参数及候选默认 5 秒见 D03；该秒数不是业务 timeout，也不承诺外部动作撤销。

**验收 R03-02**：业务尚未退出时可观察取消终态，新运行和编辑被拒；已有另一运行正常推进；资源退出后恢复准入；分别验证 arun 和同步调用不会因受支持后端的残留工作无限等待。

### 3.3 A03-003：冻结检查与写入存在竞争窗口

**既有契约**：第 4 节，T14、T17。

**修改位置**：[node.py](../../../easy_agent/node.py) 的受管理赋值与连接入口、Graph 注册删除及运行快照生成。

**建议方法**：

- 用统一内部修改入口处理资格检查、候选校验和提交，运行取得租约及固定计划也使用同一把定义锁。
- 关联字段一次提交；禁止先更新 retry 再更新 max_attempts 而暴露中间态。
- 可能调用用户迭代逻辑的规范化可在锁外生成独立候选值；锁内重新检查租约和定义版本，再校验受影响不变量并安装。版本变化时明确冲突或重新构造候选，不能覆盖较新的修改。
- 不持锁 await；不在锁内执行业务回调。对可重入调用仍须在最终提交点重新确认资格。
- 批量编辑的所有者需能区分线程和异步任务；threading.RLock 的同线程可重入性不等于异步任务隔离。
- validate、拓扑导出和运行快照读取也应取得一致视图；不能只给写入口加锁而让只读路径观察到事务中间态。

**验收 R03-03**：用 Event/Barrier 固定“候选转换暂停—运行开始—提交恢复”的交错，只允许修改先完成进入快照，或运行先取得租约使修改失败；赋值、注册删除、route、receive 均不得穿透冻结。

### 3.4 A03-004：工具声明没有冻结

**既有契约**：第 4、6 节，T17。

**修改位置**：Node tools 声明、[tools.py](../../../easy_agent/tools.py)、编译计划、工具准入及调用适配。

**建议方法**：

- 将名称、说明、输入输出 Schema、权限、副作用和重试资格解析成不可变描述；复制并递归冻结框架拥有的可变容器。
- 实际工具参数构造、准入、执行与日志使用同一描述；不能日志读取快照、调用再读取可变名称。
- 内部 Tool 虽无图节点 owner，也记录消费其声明的运行租约。任一消费者未结束或仍清理时，受管理声明不得修改。
- 声明租约与图节点的单一所有权分开；不因此擅自禁止文档允许的内部共享。同一实例同时独立节点和内部工具的双重放置继续按既有规则拒绝。
- 函数与外部客户端是调用资源；不通过复制任意闭包或客户端制造虚假的线程安全。Pydantic 类型和调用代码的任意 monkey patch 不纳入可冻结保证，适配器支持范围需要写明。

PyTorch state_dict 返回浅拷贝并保留参数和缓冲区引用，因此只能借鉴受控注册思想，不能将浅快照等同于不可变定义。[PyTorch state_dict](https://docs.pytorch.org/docs/2.14/generated/torch.nn.Module.html#torch.nn.Module.state_dict)

**验收 R03-04**：原列表、工具名称、权限、副作用、嵌套 Schema 的变化无法改变活动计划；自定义 forward 读取受管理声明也不出现与日志不一致的值；一个消费者结束不能提前解除另一个的保护。

### 3.5 A03-005：构造器覆盖子类副作用声明

**既有契约**：第 6、14 节，T27。未显式配置时不能静默抹去现有声明。

**修改位置**：Tool 构造与声明解析。

**建议方法**：以内部缺省哨兵区分未提供与 False；按显式参数、子类继承声明、框架默认的顺序解析；有效值严格要求 bool。同步检查名称和权限是否存在同类默认覆盖，但新增发现应另行记录证据。

**新增提案 D06**：建议显式构造值允许覆盖类级默认，包括显式 False；记录有效声明来源。这与“未提供时保留类级 True”分开。若要求 True 为不可降低下限，须明确改变兼容政策，不能悄悄混入缺省值修复。

**验收 R03-05**：直接和多层继承的 True 在未传参时保留；普通工具保持已有默认；非法值拒绝；两种放置方式最终描述和实际调用次数均符合准入结果。

### 3.6 A03-006：独立工具绕过允许列表

**既有契约**：第 14.1 节，T27。两种入口具有相同准入结果。

**修改位置**：编译检查和实际工具调用入口。

**建议方法**：独立 Tool 与内部 Tool 共同调用同一个准入逻辑，依据冻结描述检查名称、权限和副作用；被拒绝时业务调用次数为零。编译阶段提前诊断，运行前置检查使用同一有效策略。

**新增提案 D07**：允许列表统一按稳定 tool_name 匹配；Graph 构造中 None 与空集合继续表示没有获准工具，不把 Graph 属性注册视为授权。当前 allowed_tools 是 Graph 级参数，本文不新增 Node.allowed_tools 或新的继承机制。Graph 节点换名不改变工具权限。

审批相关接口没有完成前，不扩大现有副作用工具执行范围；修复 allowlist 不要求先建设完整审批系统。

**验收 R03-06**：同类两个实例分别独立与内部放置，覆盖允许、空列表、None、权限不足、副作用拒绝、图属性改名；两种入口结果一致。

### 3.7 A03-007：send_to 失败保留部分修改

**既有契约**：第 13.2 节，T25。

**修改位置**：send_to、set_downstreams、路由及接收规则的单次修改入口。

**建议方法**：先解析全部候选目标，再验证所有权、有效性、连接互斥和受影响依赖，保留原顺序并按既有规则去重，最后一次提交。失败前不修改旧连接。删除边不能自动缩减 receive.sources。

单次方法不能强制初始构图已经完整；只检查本次修改及受影响约束。批量事务结束及运行前执行全图验证。

**验收 R03-07**：第一个、中间、最后一个目标非法时，旧出边、route、receive、入口和派生拓扑均不变；合法增量构图、追加和去重行为保持兼容。

### 3.8 A03-008：失败事务污染新候选实例

**既有契约**：第 13.2—13.3 节，T25—T26。

**修改位置**：graph.edit、replace_node、注册删除和候选对象状态管理。

**首选内部方案**：事务持有独立候选定义，暂存绑定、拓扑、入口与配置变化；所有操作读写该事务的候选视图；验证通过后在定义锁内统一安装。其他调用者不能读到半更新定义。

**可分阶段的修复**：为事务触及的每个实例，在第一次修改前记录原始框架状态。记录不随实例从图中删除而移除。失败恢复原图映射以及所有候选的绑定和拓扑声明，不能只扫描退出时仍注册的节点。

- 不对整个业务对象做任意 deepcopy 或清空 __dict__；只管理框架定义字段。
- 迁移要更新入边、出边、route、receive、entry；新节点有冲突拓扑时拒绝猜测合并。
- 失败保留原有实例身份及候选原始状态；成功后重建派生计划，不迁移旧运行状态。
- replace_node 的内部事务可复用调用者已拥有的 graph.edit；这不意味着开放任意嵌套编辑或保存点语义。

**验收 R03-08**：注册后删除再抛异常，候选可绑定其他图；迁移校验失败，候选不残留出边；用户异常、权限校验失败、成功迁移及批量事务内替换均有覆盖。

### 3.9 A03-009：dotenv 无值项压过有效配置

**既有契约**：第 15 节，T30。

**修改位置**：[config.py](../../../easy_agent/config.py)、配置合并及必需字段检查、现有相反断言的测试。

**建议方法**：

1. 显式文件只读取一次，在同一文本快照上执行严格语法/重复键诊断和 dotenv_values 解析，interpolate=False，不改 os.environ。
2. 无值项 None 视为未提供，空字符串保留；不能在合并前将所有 None 报为配置错误。
3. 按节点显式值、Graph 显式值、系统环境、指定文件、默认值合并。
4. 仅对实际调用需要的最终字段做缺失及空值检查；高优先级空字符串若非法，应报错而非静默回落到低优先级。
5. 固定运行快照；自定义密钥引用进入解析集合，秘密不进入诊断正文。

python-dotenv 区分无值 KEY 与空值 KEY=；严格诊断应基于库的解析能力适配，不重新发明 dotenv 语法。[python-dotenv](https://bbc2.github.io/python-dotenv/)

**验收 R03-09**：无值文件项不覆盖显式值、环境值或默认值；必需空值失败；核对插值表达式实际保持字面值；非法/重复项脱敏报错；无模型调用的 Tool 不索要模型密钥；运行后文件变化不改变有效配置。

### 3.10 A03-010：验证结果没有成为实际 Info

**既有契约**：第 6.1 节，T06。

**修改位置**：Schema 适配、输入准备、输出规范化及 Info 来源关系。

**建议方法**：适配器返回规范化数据，而非仅返回“是否通过”。Pydantic 验证使用 strict=True，取得模型结果，再按 JSON 模式导出并检查 Info 兼容性。输入规范化后交给 forward；输出规范化后才能参与路由和下游执行。[Pydantic Serialization](https://docs.pydantic.dev/latest/concepts/serialization/)

- 模型声明的默认字段和 validator 结果属于用户 Schema，不是框架自行猜测补字段。
- 输入或输出内容改变时创建新的不可变 Info、重新计算 content_hash 并关联原输入；无变化的合法透传遵守既有身份规则，不能一律生成新 ID。输入派生的 origin_kind 及 Schema 标签映射属于 D08 的精确协议选择。
- 校验器在同一边界只执行一次，提交门禁不再重复校验。建议首次输入验证成功后，在逻辑执行中固定规范化输入供后续尝试复用，避免对已规范化值反复应用非幂等 validator；首次验证仍受首个 attempt deadline 约束，输出则每个 attempt 分别验证。该缓存和身份规则应随 D08 一并写清。
- JSON 兼容不代表任意自定义 serializer 都满足接收方 Schema。序列化/验证模式及别名政策须明确，不能通过再次验证造成无穷规范化或声称任意模型可往返。
- 校验或序列化失败不退回原数据冒充成功；耗时受 A03-001 约束。

**验收 R03-10**：默认字段、去空格、嵌套值、extra ignore/forbid、严格类型、序列化失败、来源关系及路由读取规范化值；审计样例正式输出包含 text=hello 和 count=7。

### 3.11 A03-011：重试路径被常量关闭

**既有契约**：第 7、11、14 节，T09—T10、T22、T28—T29。

**修改位置**：错误分类、尝试调度、资源名额、适配器错误映射及外部动作记录。

**建议方法**：

- 用可机器判定的故障类别代替 retryable=False；不能按异常文本或所有 Exception 判断。
- 框架期限、取消、配置、权限、输入 Schema、确定性业务错误和预算耗尽不重试。可信适配器识别的瞬态故障再检查副作用资格。
- 失败后释放 Graph 与 Node 的活动名额，将逻辑执行放入可取消退避队列；不能在仍占名额的执行循环里 sleep。
- 重新取得名额后创建下一次尝试、deadline 和预算；保留 node_execution_id，递增 attempt；max_steps 在实际开始尝试时计数。
- 上一尝试残留活动尚未退出或被验证隔离时，不得开始可能重复动作的下一尝试；释放计数器不代表旧业务已结束。
- 失败尝试局部正文与历史不进入下一轮成功上下文，但故障、已发生动作及真实消耗不得被丢弃。
- 关闭并验证 SDK 隐式重试。不能关闭或观测的适配器不能声称满足统一次数保障。
- 退避任务属于可推进活动；MissingInput 检查不能漏掉它。

**新增提案 D04**：初始间隔 0.5 秒、倍数 2、本地上限 8 秒、可测试随机源；抖动及 Retry-After 规则详见第 6 节。输出解析/输出 Schema 默认不重试，允许显式开启但不能绕过副作用限制。

LangGraph 的 max_attempts 也包含首次，但其默认超时重试规则与本项目不同；仅借鉴策略分离，不改变本项目超时立即停图要求。[LangGraph Fault Tolerance](https://docs.langchain.com/oss/python/langgraph/fault-tolerance)

**验收 R03-11**：两次失败第三次成功恰为三次；全部失败无第四次；不可重试故障一次；退避不占名额且响应取消；下一 attempt 计时始于重新取得名额；不安全或未知动作阻止整轮重放。

### 3.12 A03-012：无序完成集合决定投递

**既有契约**：第 9、11、12 节，T18—T22、T31—T33。

**修改位置**：完成事件收集、协调器提交、Info 投递和接收序号。

**建议方法**：尝试向协调器提交候选完成/失败通知，由协调器入口分配单调序号、按队列顺序处理。来自 Worker/线程的通知通过受控 IPC 或事件循环桥接，不能直接修改运行状态。

- 顺序定义为协调器观察到的顺序，不宣称还原跨线程绝对物理先后。
- NodeSucceeded 在协调器正式提交时产生，后续投递登记与提交保持一致。
- sequence 的到达事实在接收区单独编号；完成事件序号不与输入接收游标混为一谈。
- 失败终态之后拒绝后续提交和未执行投递；此前已提交分支不做隐式回滚。
- 不按节点名、任务地址、时间戳或 sources 列表排序 done 集合来伪造合法顺序。

**验收 R03-12**：用屏障控制通知顺序，覆盖正序、逆序、同批成功失败交错；验证停止后的提交数为零、跨 run 隔离；all 继续按声明来源组装一次，sequence 对真正逆序明确失败。

## 4. P03 未完成能力的推进方案

### 4.1 P03-001：模型调用边界

**已有行为**：沿用 v0.3 第 5 节指定的首个提供商、请求模型字符串、消息映射和预算口径；本文不宣称该模型字符串对应的远端服务身份或可用性已重新验证。

**内部方案**：模型适配器接收不可变配置、当前输入、已提交历史、工具描述和尝试的剩余期限/预算，返回候选业务正文、工具调用、usage、结束原因与请求/响应身份。密钥通过私有调用上下文获取，不进入公开 runtime、Info 或普通日志。

传输客户端按运行/后端生命周期管理，不能在跨事件循环的共享 Node 上保存活动异步客户端。暂不要求公开一个新的适配器基类；先用单一实现及受控传输替身验证协议。

**待定 D01、D08**：传输依赖、公开 thinking 和严格模型身份字段，以及具体 Schema 请求映射。HTTP 客户端名称未定不影响消息、预算和错误映射的内部契约设计。真实服务验证与本地模拟测试分别报告。

### 4.2 P03-002：内部工具循环

流程为模型候选响应、校验调用请求、工具准入、参数验证、顺序执行、结果回填、检查剩余预算/期限、下一模型请求或最终结果。

普通函数使用明确的签名绑定与 Schema；Tool 保持 Info 到 Info 的边界。保留 tool_call_id 供协议关联，不将其当作跨尝试幂等键。内部工具不参与图路由、不再获取 Graph 名额，输出只回填当前模型。

usage 缺失不能填零；若需要模型续轮而无法计算可靠剩余额度，停止尝试。工具失败不能默认转成普通文本继续模型推理；哪些错误允许作为协议工具错误返回须明确列举，确定性准入及期限错误仍按运行规则停止。

**待定 D02**：显式函数包装 API、首批第三方适配名单、内部调用计数与上限。缺 docstring/类型标注时不猜参数；未支持的流式工具提前拒绝。

### 4.3 P03-003：Worker 与执行模式

建议采用 Windows spawn 兼容的可终止进程后端，首批支持可导入入口及可序列化的声明、输入和历史；不传递整张 Graph、活动事件循环或任意客户端。外部客户端在 Worker 按适配规则创建。

需要隔离整个尝试的场景包括同步业务、同步阻塞校验及显式要求隔离的不合作异步业务。不能因 Tool.forward 是 async 桥接就把其内部同步 invoke 误判为可合作异步业务。

静态能力与可导入协议检查在运行前进行；建议取得尝试名额后的实际 Worker 启动、输入传输、业务调用、输出验证与候选回传共享同一个 attempt deadline，不分别领取额外期限。动态输入的序列化能力不能全部在 validate 阶段证明，必须区分运行前可发现的问题和实际传输失败。

Worker 只报告候选结果和过程事件；监督器负责启动、收集、终止、确认退出及回收 IPC。对后端拥有的子进程资源明确追踪范围；任意用户代码自行启动的外部进程不被冒充已经回滚或全面回收。

**待定 D03**：清理参数、各 execution 值的精确定义、不可序列化对象政策、显式隔离选择方式。同步硬期限与隔离对象兼容性必须一起验收；不能以后台线程绕过待定协议。

### 4.4 P03-004：sequence 会话

复用 v0.3 已规定的静态分组及严格接收：会话键至少包含 run_id、receiver_node_id、fork_group_id。普通节点或单来源接收仍需确定的分组由协调器分配，不从输入正文猜测或只按节点名拼接。

会话维护 expected_sources、accepted_count、committed_count、pending 和 in_flight，满足 0 ≤ committed_count ≤ accepted_count ≤ 来源总数。

- B 输入合法到达后，C 可在 B 执行或退避时合法入队；C 不能在 B 成功前执行。
- B 重试不重新接收 B、不回退接收游标；每次 B 尝试使用同一已提交历史，不包含提前收到的 C 等未来轮输入。
- 只有成功轮追加不可变历史；最后一轮成功才向图下游发布一次。
- 检查缺失输入时包含待消费输入、退避、在途通知与投递；来源失败按停止规则终止等待。
- 未支持的循环、嵌套分叉和动态来源在编译时拒绝。

**待定 D05、D09**：只读历史结构、无普通广播时分组规则的完整支持范围和公开错误名称。接收/提交分离等既有行为不因类名未定而变成目标未定。

### 4.5 P03-005：故障分类与退避

按 A03-011 建立策略输入：故障来源、瞬态标记、是否存在结果未知/不可安全重复的动作、剩余尝试次数及 Retry-After。策略计算重试资格与计划时间，调度器负责可取消等待及重新入队。

**待定 D04**：数值、抖动及公开配置入口。不要把副作用账本清空来使下一尝试重新获得重试资格。

### 4.6 P03-006：动作记录与准入

先复用统一准入并建立运行内最小调用账本，记录逻辑动作标识、工具稳定名称、受保护的参数摘要、attempt 关联及 planned/started/succeeded/failed/unknown 状态。

failed 不能自动代表“动作未发生”，应另存后端可证明的执行结果；请求发出后连接中断等情况默认结果未知。账本不保存原始秘密参数，也不提供 exactly-once 保证。

跨 attempt 只有同一逻辑动作才可复用幂等标识；不能包含 attempt，也不能仅用调用序号。名称或规范化参数变化时，识别为新动作或明确冲突；没有后端幂等/核对能力就不能自行重放。

**待定 D10**：副作用与审批声明、safe_to_retry、稳定动作身份和结果核对接口、失败观察接口。完整审批与补偿系统仍不在本轮范围。

### 4.7 P03-007：错误类型

建议保留既有异常继承关系，为新增场景先列稳定错误码与安全定位字段。顺序、缺失输入、预算、后端能力、Worker 启动/序列化及清理未完成应可机器区分，避免解析中文异常文本。

配置构建前错误不伪造 run_id；运行错误保留 run_id、节点/尝试标识及因果异常。清理失败是原运行终态的附加诊断，不把已取消运行改成新的成功或掩盖原超时原因。

**待定 D09**：具体公开类名、继承和导出范围；候选名称见第 6 节。

### 4.8 P03-008：只读运行上下文

建议 node.runtime 作为只读属性，从任务局部上下文取得当前绑定，不向共享 Node 写入本次运行状态。内部工具获得父尝试关联的子调用上下文；Worker 显式接收必要的可序列化快照。

建议公开字段为 run_id、node_id、node_execution_id、attempt、session_id、round_index、成功历史和动态剩余时间；字段类型、空值及编号见 D05。公开上下文不提供密钥、可变 RunState 或协调器句柄。

绑定在执行期退出后失效；被子任务继承的上下文也必须检查租约有效性，不能仅依靠 ContextVar 值存在就允许迟到上报。步骤观测只记录作者明确上报的区间，默认不扩大全文落盘范围。

框架任务集合覆盖框架创建或明确登记的任务，不等于自动掌控用户任意 asyncio.create_task。用户后台任务的支持范围和登记方式须作为 D05 的公开边界说明，本文不自行增加 runtime.spawn 接口。

| D09 | 新运行错误 | 候选 SequenceOrderError、MissingInputError、OutputBudgetError、BackendCapabilityError、WorkerExecutionError、CleanupPendingError | 需逐项定继承与稳定 code；运行已终结后清理错误作为附加诊断，不覆盖原始终态。执行期外 runtime 访问还需确定错误类别 |
| D10 | 副作用与步骤扩展 | 运行内账本、显式重试资格和失败观察；步骤上报沿用 v0.3 的 record_step 方向 | 明确 requires_approval、safe_to_retry、幂等核对及 step 参数；不增加完整审批系统。观察 hook 不控制必要准入或恢复成功 |

**D04 的候选精确定义**：第 k 次重试（k=1 表示第一次重试）的本地间隔基数为 min(8, 0.5 × 2^(k−1)) 秒，在该基数的 1/2 到 1 倍之间均匀取样；测试注入受控随机源。有效 Retry-After 支持秒数或 HTTP 日期，换算为等待时长后，以 max(本地间隔, 服务要求间隔) 等待；不以 8 秒上限截短服务要求。无效值记录兼容诊断后使用本地退避，过去日期按零处理。等待全程可取消，不消耗下一次尝试期限。此提案没有整次运行等待上限；若产品需要，应另立总等待预算，不能拿 180 秒尝试期限暗中代替。

**D03 的决策约束**：无论 execution 名称最终如何映射，都必须满足同步调用不能静默主线程执行、显式隔离不可用时提前失败、默认 max_concurrency 含义不变。本文不以这些约束代替完整模式表，模式表未定的具体入口仍是待定项。
