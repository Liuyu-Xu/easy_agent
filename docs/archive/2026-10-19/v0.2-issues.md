# Easy Agent v0.2 实现问题清单

更新日期：2026-10-03（Asia/Shanghai）  
依据：`v0.2.md` 的 D01—D10，以及本次实现审计  
原则：只实现 v0.2 中已经确认且能够唯一推导的行为；本文件中的事项不以代码默认值代替架构决定

## 当前已落地的确定项

- 包版本更新为 0.2，项目说明指向 `v0.2.md`。
- 默认模型配置解析为 `deepseek-v4-flash`，默认 temperature 为 0，默认最大输出为 10000 Token；没有实现输入 Token 裁剪。
- Tool 继承 Node，可作为独立工作图节点接收 Info 并返回 Info。
- 默认节点并发数为 1，保留运行时并发覆盖入口。
- Graph 支持可选日志目录，默认继续使用 `.easy_agent/logs`。
- `.env` 改用 `python-dotenv` 的 `dotenv_values` 显式读取，不改写 `os.environ`。
- 运行期间禁止修改 Graph 和已注册 Node 的框架定义，日志查询和 Graph 管理的运行状态仍可更新。
- 异步节点每次尝试采用 Graph/Node 的 timeout；默认 180 秒。任意一次异步超时立即使本次 Graph 失败，不继续剩余重试，并阻止该结果向下游传播。
- 旧 `retry` 默认值调整为 2 个额外重试，使默认总尝试次数为 3；公开参数语义仍等待 V02-003 定稿。
- `all` 汇合由直接菱形扩展为无条件、无嵌套的线性多步骤分支汇合。
- 节点成功、失败、取消、重试和异步超时事件记录本次尝试的耗时。

这些条目只说明本次代码行为，不表示 D01—D10 已全部解决。

## V02-001：内置模型协议仍未确定（D01）

默认模型名称和参数已经进入配置快照，但 v0.2 没有唯一确定：

- 模型服务地址和认证协议；
- Chat Completions、Responses 或其他请求格式；
- Info、prompt、role 与协议消息的映射；
- 默认思考模式；
- 10000 Token 是否包含思考 Token，以及节点内多轮模型调用如何累计；
- 参数被服务忽略时应报错、警告还是记录兼容状态；
- 流式响应、工具调用及错误响应的规范化方式。

因此直接实例化的内置 `Node` 仍在 `forward()` 中抛出 `UnsupportedFeatureError`。代码没有根据模型名称擅自推断供应商协议。

## V02-002：正式 Schema 与节点内工具适配协议未确定（D02）

当前只保留 v0.1 的 Python 运行时类型检查。尚未确定 Pydantic、dataclass、JSON Schema 或自定义协议，也没有实现模型文本自动转换为结构化 Info。

Tool 已可作为独立 Node 使用，但以下节点内工具行为尚未实现：

- 普通函数和第三方工具如何生成名称、说明及参数 Schema；
- 从 Info 或模型工具参数到函数参数的转换；
- 工具结果如何包装并回填模型；
- 同步、异步和流式第三方工具的统一调用；
- 未注册 Tool 实例作为 `Node(tools=[...])` 时的稳定命名；
- 同一个 Tool 对象能否同时作为图节点和模型内部工具。

当前 `Node.tools` 只参与名称、允许列表和权限校验，不会自动形成可工作的模型工具循环。

## V02-003：三次机会的公开参数与普通错误策略未确定（D03）

用户确认默认总共三次机会，但 v0.2 明确没有确定公开参数名称。现有 v0.1 参数 `retry` 表示“首次之外的额外重试次数”。为了使默认行为达到三次，本次将 Graph 默认 `retry` 设为 2，没有静默把所有既有传值改解释为总尝试次数。

因此仍需决定：

- 是否引入 `max_attempts`，以及如何处理旧 `retry`；
- 用户配置的数字究竟表示总次数还是额外次数；
- 次数按每条 Info 的逻辑执行，还是按完整时序会话计算；
- 哪些 Python、模型、网络、解析或内部工具错误允许重试；
- 内部客户端自己的重试是否占用这三次；
- 非超时错误耗尽机会后是否统一使整图失败。

当前非超时错误继续沿用 v0.1 的最小异常排除规则，不能视为 v0.2 最终策略。异步超时已单独处理为立即停图且不重试。

## V02-004：同步代码的 180 秒强制停止无法由当前后端保证（D04）

异步 `forward()` 使用可取消的异步等待实施期限。同步 `forward()` 仍在当前线程执行；任意 Python 同步函数、其他线程和已经发出的远端请求无法由该执行器安全强制终止。

当前不会为同步函数伪造超时成功。若同步节点阻塞，Graph 可能无法在 180 秒时恢复控制，运行定义也会继续保持冻结。要满足同步工具的硬期限，需要先确定线程、子进程或隔离 Worker 后端，以及：

- 超时监督是否独立于业务线程；
- 停图后如何处理仍在运行的代码和迟到结果；
- 清理期限以及何时允许再次编辑 Graph；
- 排队、等待汇合、等待下一份时序输入是否具有独立期限。

## V02-005：预设顺序的时序接收尚未实现（D05）

用户已确认同一节点按预设来源顺序分次接收，并在顺序错误时显式报错，但尚未确定检查边界：

- 按上游完成顺序检查；
- 按 Info 进入 Graph 接收区的顺序检查；
- 按 Graph 正式投递顺序检查；
- 或按节点实际消费顺序检查。

也没有确定后序来源提前完成时是立即报错，还是允许暂存但仍按预设顺序交付；顺序错误是否停图、是否消耗一次机会也未确定。

因此当前 `receive()` 仍只接受 `mode="all"`。其他模式会抛出指向本文件的 `UnsupportedFeatureError`，没有擅自选用 `ordered` 或 `sequence` 作为正式 API。

## V02-006：时序会话的历史提交和结果发布未确定（D06）

用户已确认后续轮次保留此前输入和输出，但仍需确定：

- 每轮结果都发送下游，还是只发送最后一轮；
- 会话结束条件；
- 如何维持 Graph 的唯一最终结果；
- 三次机会按单轮还是整段会话计算；
- 失败尝试和部分输出是否进入后续上下文；
- 循环或多次分叉时如何区分时序会话实例。

当前没有在 Node 对象上添加共享历史，也没有实现时序运行状态，避免跨 GraphRun 串用上下文或产生未经确认的多结果行为。

## V02-007：并发限制的跨运行范围未确定（D07）

当前 `max_concurrency` 只限制一次 GraphRun 内同批就绪节点的执行数量；节点信号量也属于单次运行。同一 Graph 的多个并发调用不会共享全局额度。

尚未确定：

- 是否需要同一 Graph 跨运行共享限流；
- 外部模型账户是否需要独立的全局限流器；
- 节点内部多个工具调用是否可以并行，以及是否占用 Graph 节点并发额度；
- 时序接收等待队列与并发名额的最终关系。

当前默认并发 1；只有 `execution="async"` 时，提高 `max_concurrency` 才会并发调度多个就绪节点。`sequential` 模式继续逐个执行。

## V02-008：模型与工具日志的业务指标口径未确定（D08）

本次为所有受 Graph 管理的节点尝试增加了总耗时，但没有将它冒充为模型首字响应时间、完整模型响应时间或任意工具内部步骤时间。

下列要求仍需具体协议或上报接口：

- 思考内容的保存、脱敏和访问范围；
- 首字时间、生成时间和整轮节点耗时的区别；
- 输入、输出及思考 Token 的来源；
- “命中率”是否专指缓存命中 Token 比例；
- “信息分布处理情况”的字段和统计定义；
- 工具内部调用与步骤耗时的显式上报；
- 配置并发、实时并发和峰值并发的区别。

内置模型协议尚未实现，因此当前也无法产生真实模型统计。第三方 Python 函数的内部步骤不会被框架自动猜测。

## V02-009：Node 下游查看与修改 API 未确定（D09）

用户已确认需要下游列表查看和修改能力，但 v0.2 尚未确定：

- 属性或方法名称；
- 追加、整体替换、删除单个目标和清空的语义；
- 条件 route 如何查看和修改；
- receive 来源是否随连接变化自动更新；
- 节点替换时旧连接是否显式迁移。

当前继续保留 `send_to()`、`route()` 和 Graph 的只读 `relations`。没有新增另一套 `graph.connect()`，也没有允许用户直接修改 `_outgoing`。在 API 定稿前，旧连接的完整公共修复入口仍缺失。

## V02-010：安全回退扩展点与工具审批范围未确定（D10）

用户决定本版不实现安全回退，但“保留扩展接口”的准确形态尚未确定。当前没有新增用户必填的策略对象，也没有实现外部动作补偿、回滚或不可信代码沙箱。

v0.1 已有的密钥保护、工具允许列表和权限检查仍保留。声明 `side_effect=True` 的节点内工具仍因审批协议未定而被拒绝；独立 Tool 节点的副作用声明、审批和重试规则还没有统一协议。

## V02-011：python-dotenv 的插值选项和非法行策略未确定

代码已经按确认使用 `python-dotenv`，显式传入文件路径，并通过 `dotenv_values` 避免修改 `os.environ`。当前采用该函数的默认插值行为。

v0.2 尚未确定是否禁用变量插值、无值变量如何处理，以及非法行应当警告还是使 Graph 配置失败。因此这部分不能视为最终配置语法契约。

## V02-012：多步骤汇合当前限定为可静态验证的线性分支

用户确认支持多步骤分支汇合；本次实现支持以下形态：

```text
        → B → E ┐
A               → D(all: E, C)
        → C ────┘
```

各分支可以有不同数量的节点，但必须无条件、无线内再次分叉、无内嵌汇合，并由声明的终端来源无条件且仅发送到汇合节点。运行时沿分支传播同一分叉组标识。

v0.2 明确没有自动扩展到任意动态分支、嵌套并行循环或未知数量汇合，因此这些结构继续明确拒绝。若以后需要扩大范围，应先补充架构规则，而不是放宽校验后猜测配对关系。
