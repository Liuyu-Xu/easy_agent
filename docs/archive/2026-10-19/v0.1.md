# Easy Agent v0.1 架构设计

文档版本：0.1  
更新日期：2026-10-03  
状态：架构设计基线，尚不代表 SDK 已实现  
依据：本项目关于信息流、执行模式、安全、日志及 PyTorch 风格接口的讨论

## 1. 目标与设计原则

Easy Agent 暂定为一个以信息流为核心的 Agent 工作流搭建库。用户创建工作图，在图中实例化节点，由节点声明输出流向，再向图输入信息即可运行。

公开的核心抽象固定为三个类：

> **Graph 管理整个运行，Node 定义处理行为与输出去向，Info 承载数据与来源。**

设计目标：

- **便捷**：自动注册节点，提供可调用的 Graph；默认行为覆盖简单工作流；复杂能力按需启用。
- **透明**：全局设置、节点间通信、节点内部活动和信息来源均可查询；自动行为有记录。
- **安全**：统一处理密钥、权限、审批和日志内容策略，明确框架能够实施的安全边界。

借鉴 PyTorch 的组件属性注册、构造与执行分离、`forward()` 扩展和可调用对象体验。不要求依赖 PyTorch，也不引入 Tensor、自动微分或训练语义。

用户无需手动创建 `EdgeSpec`、`CompiledGraph`、`GraphRun`、执行器或日志存储对象，也无需重复编写 `Graph.forward()` 来描述已经声明的节点连接。内部可以存在这些机制，但不作为基础使用的前置知识。

本版暂不设计可视化界面，仅保留节点、关系、日志和来源记录的导出能力。

## 2. 最小使用体验

以下代码是拟定 API，用于说明接口契约；模型名为占位值，不代表真实可用的模型。

```python
from easy_agent import Graph, Node, Info

graph = Graph(env_file=".env", execution="async")

graph.writer = Node(
    model="writer-model",
    prompt="根据用户主题撰写初稿。",
)

graph.editor = Node(
    model="editor-model",
    prompt="检查并润色收到的初稿，返回最终正文。",
)

graph.writer.send_to(graph.editor)

result = graph(Info("写一篇关于城市绿化的短文"))
print(result.text)
```

上述调用自动完成节点注册、入口与出口识别、配置解析、连接校验、调度、信息投递、日志记录和最终结果封装。

复用整个工作流时，可以继承 Graph：

```python
class WritingGraph(Graph):
    def __init__(self, **options):
        super().__init__(**options)
        self.writer = Node(prompt="根据主题撰写初稿。")
        self.editor = Node(prompt="润色收到的初稿，返回最终正文。")
        self.writer.send_to(self.editor)


graph = WritingGraph(env_file=".env", execution="async")
result = graph(Info("介绍城市绿化"))
```

省略节点模型配置时继承 Graph 的默认模型设置。没有可用模型设置的内置 LLM 节点必须在发出外部请求前报错。

## 3. 三类职责与协作关系

| 类 | 负责 | 边界 |
| --- | --- | --- |
| Graph | 拥有并注册节点；解析全局配置；校验工作图；调度和投递；实施有效安全策略；汇集运行记录 | 不维护第二套用户可编辑路由；不承担具体节点的业务处理 |
| Node | 定义一次处理行为；配置模型、提示词和工具；声明输入输出契约、出站规则与接收规则 | 不递归执行下游；不自行创建工作图调度器；不绕过 Graph 投递信息 |
| Info | 承载业务数据、数据契约和来源标识；提供简单读取与派生能力 | 不保存节点或图实例、密钥、调度命令、日志存储或可执行工具 |

完整运行过程：

```text
用户提交 Info
    → Graph 选择入口并安排执行
    → Node 处理输入，返回 Info
    → Graph 按该 Node 的出站规则评估去向
    → Graph 向目标 Node 投递 Info
    → 重复执行，得到唯一逻辑结果
    → Graph 发布最终 Info
```

关键职责划分：

- **Node 声明“交给谁”，Graph 执行“何时、如何交付”。**
- **Node 声明“需要哪些输入”，Graph 判断输入是否齐备。**
- **Node 声明“需要哪些能力”，Graph 的有效策略决定是否授权。**
- **Node 活动产生事件，Graph 管理事件接收与存储；两级日志按范围查询。**
- **Info 携带来源标识，完整活动过程存储在日志中。**

## 4. Graph：工作图与运行入口

### 4.1 节点注册和所有权

```python
graph.writer = Node(...)
```

赋值时自动注册节点。第一版约定：

1. 每个 Node 实例只能绑定到一个 Graph，并具有一个注册名称。
2. 属性名作为节点的可读名称，例如 `writer`；内部标识由框架生成。
3. 将同一实例再次绑定为其他节点或绑定到另一张图时，应明确报错。
4. 复用配置或实现可创建新节点实例；共享模型客户端由内部资源管理机制处理。
5. 连接目标必须已经注册到同一个 Graph。
6. 节点连接保存内部节点标识，不把目标节点当成自己的子节点注册。
7. 普通 Python 列表中的节点不被隐式扫描注册；需要批量创建时显式赋给 Graph 属性。专用节点容器可后续扩展。
8. 构造顺序建议为：先实例化并注册节点，再设置连接。

运行快照中的节点身份和配置保持固定。节点删除、替换或重新连线使后续执行计划失效，下次运行重新校验；已经开始的运行不受影响。

### 4.2 内部机制与用户接口

Graph 内部可以拆分注册表、计划校验器、调度器、执行器、配置解析器、权限执行器和事件存储。这是内部实现分工，不要求用户逐个实例化。

典型公开接口：

| 接口 | 行为 |
| --- | --- |
| `Graph(...)` | 创建图，设置全局默认值 |
| `graph.node_name = Node(...)` | 注册节点 |
| `graph(info)` | 阻塞执行，成功时返回 Info |
| `await graph.arun(info)` | 异步等待执行，成功时返回 Info |
| `graph.entry = node` | 显式指定入口，循环或入口不唯一时使用 |
| `graph.validate()` | 可选的提前检查；正常调用也自动检查 |
| `graph.relations` | 只读二维关系视图 |
| `graph.logs(run_id=...)` | 查询 Graph 级日志 |
| `graph.audit(run_id=...)` | 查询审计记录 |
| `graph.to_dict()` | 导出声明式定义，排除密钥及运行时对象 |

运行失败时抛出携带 `run_id` 的明确异常，便于继续查询日志。不得把异常文本伪装成正常 Info 返回。

### 4.3 入口和结果

- 简单无环图只有一个零入度节点时，可自动将其作为入口。
- 入口不唯一或图中存在回路时，要求显式设置 `graph.entry`。
- 注册后从入口不可达的节点在运行前报告错误，避免节点悄然脱离工作流。
- 没有出站规则的节点，其输出成为当前路径的结果候选。
- `graph.END` 是终止当前路径并提交结果候选的标记，不是需要创建的 Node。
- 一次成功调用必须具有唯一逻辑结果。互斥分支可以分别到达终点；并行分支必须先显式汇合后形成单个结果。
- `END` 不自动取消其他仍在执行的路径，也不采用“最后完成者获胜”。
- 静态可发现的多结果结构应提前拒绝；运行时出现零结果或多个结果候选时明确失败。
- 所有已启动工作和必要日志完成收尾后，才将运行标记为成功。

## 5. Node：处理行为与局部声明

### 5.1 内置节点与自定义节点

直接实例化 `Node(model=..., prompt=...)` 表示内置 LLM 节点。

自定义处理继承 Node，覆盖 `forward()`：

```python
class StripText(Node):
    def forward(self, info: Info) -> Info:
        return Info(info.text.strip())
```

异步处理可以实现 `async def forward(...)`。一个节点采用其中一种形式，Graph 的执行包装器统一调用。

`forward()` 只处理本次输入并返回 Info。节点返回的是业务信息，调度去向由出站规则决定，不要求返回 `NodeOutput` 或控制命令。

执行包装器负责输入输出校验、节点生命周期、模型与工具调用追踪、有效权限注入以及来源记录。用户手动调用 `forward()` 仅等同于普通 Python 函数调用，不构成受框架管理的运行。

### 5.2 节点配置

普通用户主要配置：

- 模型名、提供方、服务地址。
- 提示词、角色定位、上下文构建规则。
- temperature、输出 Token 上限。
- 可用工具、结构化输出要求。
- 输出去向。

按需提供的配置：输入 Schema、输出 Schema、输入预算、超时、重试、最大并行度、接收与汇合规则、权限需求。

输入 Token 预算由框架用于限制或裁剪上下文；输出 Token 上限传给模型适配器，两者分别配置。模型不支持的参数必须明确报错或通过显式兼容策略处理，不静默忽略。

节点的角色描述属于提示词配置；消息协议中的 system/user/assistant 角色属于模型适配逻辑，应区分业务角色与协议角色。

Graph 默认模型配置可被节点局部配置覆盖。安全限制不采用普通参数覆盖规则。

### 5.3 运行状态归属

Node 实例保存定义，不保存唯一的“当前输入”“当前输出”或“当前状态”。

同一节点可能参与多个 Graph 运行，也可能在一个循环中执行多次。状态和日志必须通过 `run_id`、`node_execution_id` 与 `attempt` 区分。

| 标识 | 含义 |
| --- | --- |
| `node_id` | 图中的节点身份 |
| `run_id` | 一次工作图运行 |
| `node_execution_id` | 该运行内节点的一次逻辑执行；每轮循环重新生成 |
| `attempt` | 同一次逻辑执行的重试序号 |

## 6. Info：统一信息流协议

### 6.1 用户可见接口

```python
text_info = Info("一段文字")
text_info.text

structured_info = Info({"approved": True, "comment": "通过"})
structured_info.data["approved"]
structured_info.get("approved", default=False)
```

- `data` 是唯一权威业务数据。
- `text` 是字符串数据的便捷读取方式，不是与 data 并列的第二份内容；非文本数据使用 `.text` 应明确报错。
- `.get()` 第一版只处理字典键，不引入隐式 JSONPath 解析。
- 字符串模式匹配可直接使用 `.text` 与普通 Python 字符串或正则操作。
- 强类型 `Info[T]` 和 Schema 校验作为进阶能力，简单文本使用不要求先定义类型模型。

内部记录可以包含：`id`、Schema 标识与版本、数据或制品引用、来源类型、生产运行 ID、生产节点及执行 ID、父信息 ID、创建时间和必要的数据分类标签。

来源元数据由框架生成并核验，用户传入的同名字段不得伪造框架来源或审批记录。

### 6.2 不可变性与跨进程传递

- Info 一旦进入正式信息流，其数据与来源记录不可原地修改。
- 不可变性应覆盖嵌套字典、列表等对象，不能只冻结顶层属性。
- 实现可采用递归只读表示或隔离副本，读取接口保持一致。
- 大文件、图片和其他大型对象通过制品引用传递，避免每个进程复制全部内容。
- 跨进程传输采用明确的可序列化数据格式；未注册或不可序列化类型提前失败。
- 模型客户端、HTTP 会话、文件句柄、函数对象、锁和密钥不进入 Info。

### 6.3 来源与运行归属

节点产生新业务数据时，框架生成正式输出 Info，并将本次输入信息记录为父来源。

节点原样返回收到的 Info 时，保留信息 ID，仅增加节点处理与投递事件。

为保证 `result.run_id` 总是指向当前调用，Graph 在成功出口执行一次显式的**结果发布**：创建 `origin_kind="graph_output"` 的 Info，关联实际终端 Info，业务数据可复用不可变内容引用。

因此：

- 节点之间原样转发不制造新信息版本。
- Graph 结果发布是独立的边界事件，并不表示业务正文被改写。
- 跨运行输入可以保留原来源；当前运行通过消费事件关联它。
- 即使整个工作流只是透传，最终结果也具有当前运行的 `run_id`。
- 用户创建的初始 Info 可以尚无运行归属。

来源链表示已记录的数据依赖，不代表能够恢复未保存的正文，也不等于模型的完整推理解释。

## 7. 流向与关系存储

### 7.1 唯一关系来源

节点的出站声明是唯一可编辑的关系定义：

```python
graph.a.send_to(graph.b)
graph.b.send_to(graph.c)
```

Graph 根据声明生成只读关系索引：

```text
relations[source_node_id][target_node_id] → 连接描述集合
```

内部使用稀疏二维映射，并派生入边、出边索引。连接描述至少包括源、目标、条件及必要的数据选择信息。

初版不提供另一套 `graph.connect()` 作为常规编辑入口，也不允许直接改写 `graph.relations`。关系只声明一次，索引自动更新。

`send_to()` 与 `route()` 是构造期配置方法，不立即发送数据；第一版不支持链式连接调用，方法返回 `None`，避免把广播误解为顺序执行。

### 7.2 无条件投递

```python
graph.a.send_to(graph.b, graph.c)
```

表示每次 A 成功输出后，分别投递给 B 和 C。

重复配置相同目标不产生重复投递；框架可以发出重复声明提示。顺序执行模式只改变执行调度，仍保留广播的业务语义。

### 7.3 条件路由

```python
graph.reviewer.route(
    field="approved",
    cases={
        True: graph.END,
        False: graph.writer,
    },
)
```

此处要求 reviewer 输出的 Info.data 是包含 approved 字段的结构化数据。

第一版采用字段值匹配的互斥路由：

- 每次只选一个分支。
- 字段类型必须符合声明，布尔、数字、字符串不进行隐式互换。
- 字段缺失、类型错误属于输入契约错误。
- 类型正确但值未匹配时，可以使用显式 `default=`；没有默认分支则报路由错误。
- 同一个节点不能同时声明无条件广播和条件路由；冲突在构造或校验阶段报错。
- 分支引用现有节点或 `graph.END`，不允许随意跳到未注册目标。
- 路由记录字段引用、规则和选择结果；具体字段值是否保存受日志内容策略约束。

通用表达式、第一匹配谓词、全部匹配和自定义路由插件可后续扩展，不能在第一版中依赖任意 `eval`。

### 7.4 数据选择

默认向下游传递完整 Info。需要筛选或改写字段时，第一版使用普通自定义 Node 生成新的 Info，并保留来源链。

声明式端口、字段映射和自动类型适配属于进阶扩展。它们不得使同一字段在 Node 和 Graph 中拥有两套映射定义，也不得静默丢失数据。

## 8. 接收、并行、汇合与循环

### 8.1 默认接收行为

多条入边默认表示每次收到一条信息就独立执行一次。多个上游不会自动合并，也不会自动组成对话历史。

节点只看到本次被投递的数据。需要历史对话、共享记忆或额外输入时，应显式声明，不默认读取全图日志或所有节点输出。

### 8.2 显式汇合

```python
graph.source.send_to(graph.searcher, graph.reviewer)
graph.searcher.send_to(graph.summary)
graph.reviewer.send_to(graph.summary)

graph.summary.receive(
    mode="all",
    sources=[graph.searcher, graph.reviewer],
)
```

源节点的 send_to 创建连接。目标节点的 receive 只声明接收契约，Graph 验证对应入边存在。

完成汇合后，summary 仍接收一个 Info。其 data 按来源名称组织，保存各来源的数据；父信息列表指向各输入 Info。用户无需额外操作 InputBundle。

第一版 `all` 汇合限定为可识别的结构化分叉与汇合：

- Graph 为每次广播生成分叉组标识。
- 同一汇合只组合相同 run 和同一次分叉组的输入。
- 每个声明来源在该分叉组内必须恰好提供一个结果。
- 重复输入、分组不一致或不可配对时明确报错。
- 某个必需分支失败时，不能无限等待；运行进入错误处理。
- 必需来源在条件分支中被跳过的结构不能直接使用 all 汇合。
- 汇合结果按声明来源排序，不按完成时间排序。

任意嵌套循环与复杂动态汇合不属于第一阶段支持范围。对于无法证明可配对的结构应拒绝，而非猜测如何合并。

### 8.3 循环

```python
graph.entry = graph.writer
graph.max_steps = 20

graph.writer.send_to(graph.reviewer)
graph.reviewer.route(
    field="approved",
    cases={True: graph.END, False: graph.writer},
)
```

回传给 writer 的 Info 必须包含后续修订需要的正文、意见等数据，不能假设 writer 自动读取前一次输出。

- 每次重新激活节点产生新的 node_execution_id。
- 重试沿用同一个逻辑执行 ID，增加 attempt。
- max_steps 限制整次运行的节点执行尝试总数，包含重试；并发调度下原子计数。
- 达到上限时明确标记为执行上限错误，不伪装为正常完成。
- 第一阶段支持有界单路径反馈循环，复杂并行循环后续扩展。
- 存在出口不代表一定能够终止，运行预算仍然必须实施。

## 9. 执行模式与调用约定

```python
result = graph(info)
result = await graph.arun(info)
```

两种调用成功时都返回 Info。前者阻塞调用方，后者允许调用方异步等待。内部执行配置不改变返回类型。

在已经运行的异步事件循环中使用 graph(info) 时，应提示改用 await graph.arun(info)，不得隐式嵌套或修补事件循环。

| 执行模式 | 约定 | 实施位置 |
| --- | --- | --- |
| sequential | 每次执行一个就绪节点，便于调试 | 第一阶段 |
| async | 在一个进程中并发执行依赖已满足的异步节点 | 第一阶段 |
| multiprocess | 协调器通过本地进程池执行兼容节点 | 第二阶段 |
| hybrid | 按明确配置混用异步执行和进程 Worker | 后续扩展 |
| auto | 根据可解释规则生成执行规划并记录 | 后续扩展 |

接口预留不代表已支持；尚未实现或不兼容的模式必须明确报错，不能静默降级。

异步模式不会自动加速 CPU 密集的同步 forward。阻塞任务需要受支持的执行后端；线程适配若提供，必须显式约定和记录。

### 9.1 多进程规则

- Graph 协调器负责激活、路由、投递、运行状态和事件接收。
- Worker 执行单次节点任务，返回正式结果与活动事件。
- Worker 不自行读取整份 .env，不独立修改图的全局状态。
- 客户端在 Worker 内按配置初始化，不能跨进程传输已打开的连接。
- 自定义节点类必须可导入，声明和 Info 必须可序列化。
- 并发上限、进程数、队列容量和超时由 Graph 统一控制。
- Windows 等 spawn 启动环境下，应用启动入口遵守 Python 的 `if __name__ == "__main__":` 保护要求。

### 9.2 一致性、重试与取消

各模式保持依赖关系、输入契约、路由规则、汇合规则和权限约束一致。外部模型输出、调用时序和耗时不保证相同。

取消和超时只表示运行时停止等待或请求停止，不自动证明远端请求或同步 Worker 中的操作已经终止。结果必须记录为已取消、已停止或结果不确定等实际状态。

具有副作用的工具不能因为超时就自动重试。需要幂等键、执行结果核对或重新批准；框架不宣称对任意外部操作提供 exactly-once 保证。

## 10. 配置与 .env

Graph 是配置入口，节点继承允许继承的默认值。为减少基础使用负担，第一版约定可选的默认键：

```dotenv
EASY_AGENT_PROVIDER=example-provider
EASY_AGENT_MODEL=example-model
EASY_AGENT_BASE_URL=https://api.example.com/v1
EASY_AGENT_API_KEY=replace-with-local-secret
```

通过 `Graph(env_file=".env")` 显式加载。多个模型账户可通过节点上的 `api_key_env="OTHER_API_KEY"` 等引用配置，不要求用户将密钥字面量写进 Node。

普通配置优先级：显式运行覆盖值 > 节点局部配置 > Graph 构造配置 > 操作系统环境 > 指定 .env > 库默认值。

第一版允许的运行覆盖项应是明确白名单，例如执行资源与预算；不提供任意嵌套字段覆盖。拓扑与节点声明的修改通过原有图定义接口完成。

约定：

- 明确解析 env_file 的路径，不向父目录无限搜索。
- 配置加载器读取文件为运行配置，不改写整个进程的 os.environ。
- 只解析被模型、节点或工具声明引用的配置。
- 一次运行开始时冻结有效配置；文件变更只影响后续运行。
- 全局日志记录非敏感有效值、配置来源和密钥引用，不记录密钥值。
- 公开导出不包含 .env、令牌、客户端实例或已解析的密钥。
- 仓库应忽略实际 .env，只提交不含真实秘密的 .env.example；库不得擅自修改用户仓库文件。
- .env 是本地配置载体，本身不提供加密存储。

安全策略采用授权范围交集和拒绝优先规则，不适用上述普通配置覆盖顺序。

## 11. 工具与安全边界

工具作为 Node 的能力使用，保留预定义工具和自定义工具子类。对图而言，业务信息仍然通过 Info 传递。

```python
graph.researcher = Node(
    prompt="使用可用工具查找资料。",
    tools=[SearchTool()],
)
```

工具内部可使用 Info 输入输出协议；模型只看到所需的工具参数 Schema，不看到 Info 的所有来源字段、日志或秘密。

Graph 管理以下策略：允许的工具、节点可访问的密钥、外部动作审批、已注册节点与工具类型、日志内容访问。

Node 声明所需能力；没有获得授权的框架管理调用，在实际访问资源前失败。模型产生的工具调用只是一项请求，不能等同于获得授权。

框架可实施的限制必须与实际后端能力一致：

- 内置模型和工具适配器通过受控配置获取必要密钥。
- 原始密钥不进入 Info、拓扑、普通异常和日志。
- 可序列化定义通过受信注册表加载，不执行不可信 pickle、任意导入或 eval。
- 自定义 Python 节点与工具在普通本地进程中属于受信代码，仍拥有运行账号的权限。
- 多进程只提供执行与一定故障隔离，不等于文件、网络或密钥安全沙箱。
- 不可信代码执行、系统级网络限制及多租户隔离需要独立的隔离后端，后续实施。

## 12. Graph 日志与 Node 日志

采用“团体活动日志与个人工作日志”的分层方式。底层统一事件协议，上层按范围查询；审计作为单独的事件类别和访问范围。

### 12.1 Graph 级日志

记录组织级活动：

- 图标识、定义版本、拓扑摘要。
- 执行模式、资源限制、非敏感配置快照。
- 安全和日志策略版本或摘要。
- 节点调度、分支选择、汇合等待、循环与预算消耗。
- 节点间通信、结果发布、运行完成或失败。
- 聚合 Token、耗时、重试次数和可获得的成本估算。

通信事件应区分投递请求、接收确认和节点消费，不能仅凭发送成功推断下游已经处理。

典型字段包括：源/目标节点、源/目标节点执行 ID（已知时）、连接 ID、Info ID、投递 ID、分叉组标识、投递状态、排队与交付时间。

### 12.2 Node 级日志

记录个体活动：输入接收与校验、处理状态、模型请求、工具调用、结构化输出解析、结果产生、异常、重试和审批等待。

节点主生命周期采用：

```text
ready → queued → running → succeeded / failed / cancelled
```

模型等待、工具等待、审批等待和重试等待作为活动或子状态，避免把同一节点中的并行调用压成一个互斥状态。

模型调用日志包含可获得的模型标识、参数、提供方请求 ID、提示词版本或摘要、输入输出引用、Token、结束原因、耗时和错误。未知 Token 或成本记录为未知，不填作零。

只追踪可获得的请求、公开输出、工具调用和显式判断字段；不承诺获取隐藏推理过程。

### 12.3 关联、排序和写入

统一事件信封包含：

```text
event_id, event_type, run_id
trace_id, span_id, parent_span_id
node_id, node_execution_id, attempt
info_ids, delivery_id, cause_event_id
worker_id, local_sequence, commit_sequence, timestamp
```

不适用的字段可以为空。

- span 关联 Graph、节点、模型和工具活动。
- delivery_id、cause_event_id、Info 来源关系表达因果联系。
- commit_sequence 是协调器接收并提交事件的顺序，不代表跨进程事件真实发生的全局先后。
- 时间戳用于观察，单进程耗时优先使用单调时钟。
- 重发事件以 event_id 去重；队列使用有界缓冲与背压。
- 必要状态、通信和审计事件不随意采样；流式文本片段可以合并或按策略不保存。
- 必要日志写入失败必须显式反映在运行结果中，不能声称追溯完整。已经发生的外部副作用也不能因此被认为已回滚。

### 12.4 查询接口

```python
result = graph(Info("任务"))

graph.logs(run_id=result.run_id)
graph.editor.logs(run_id=result.run_id)
graph.audit(run_id=result.run_id)

graph.editor.logs(
    run_id=result.run_id,
    node_execution_id="execution-id",
)
```

日志查询应支持过滤、分页或迭代读取，避免一次加载全部记录。Graph 的实例不在内存中保留所有历史日志。

可以提供最近运行的便捷查询，但正式追溯必须使用明确 run_id。

### 12.5 默认内容策略

默认记录元数据、来源、状态及非敏感配置，不保存完整 Prompt、模型响应、工具参数和业务正文。

完整内容捕获必须显式开启，并受字段脱敏、访问范围和保留期限限制。脱敏在写入前完成；模板中的敏感内容同样受策略约束。

哈希用于内容校验或比较，并不自动匿名化敏感数据，也不构成防篡改证明。

本地初版日志的读取边界依赖运行账号和存储文件权限。多人访问授权、独立审计存储和加密内容后端作为后续能力实施，不以 Python 查询接口替代系统隔离。

## 13. 追溯、记录回放与恢复

第一阶段交付日志查询、信息来源追溯和已记录事件的查看。以下能力逐步扩展：

| 能力 | 定义 | 前提 |
| --- | --- | --- |
| 事件回放 | 按记录展示历史活动，不重新执行节点 | 活动事件存在 |
| 记录驱动执行 | 使用已保存的模型/工具响应或节点输出继续测试 | 对应正文、版本、调用匹配信息完整 |
| 实时重执行 | 使用指定配置重新调用节点与外部服务 | 重新验证权限和输入，接受结果变化 |
| 检查点恢复/分叉 | 从持久化状态恢复，或使用新配置创建新运行 | 调度状态、待处理输入、版本与副作用记录完整 |

只保存 ID、哈希和元数据时，无法还原已丢弃的正文，记录驱动执行应明确报告缺失。

模型输出替换可以使外部调用部分可复现，但不自动使包含随机数、时钟、任意自定义代码和副作用的整个系统确定化。

具有副作用的工具在回放时默认使用已有结果或 Mock，不再次执行。实时重执行需要满足新的授权和幂等要求。

检查点恢复不能只持久化 Info；还必须保存调度状态、投递状态、汇合分组和已提交动作。完整崩溃恢复不属于第一阶段承诺。

## 14. 实施范围与顺序

v0.1 是架构文档版本。下列阶段用于控制实施范围，并非已完成的功能清单。

### 第一阶段：最小完整体验

- Graph、Node、Info 三个公开核心类。
- 属性自动注册、源节点 send_to、字段值条件 route。
- 入口/出口约定、唯一结果发布、基础验证。
- 简单链、互斥分支、结构化广播与 all 汇合、有界单路径循环。
- 内置 LLM 节点、自定义 forward、工具扩展接口。
- sequential 与 async；配置和日志接口保持稳定。
- 显式 .env 加载、密钥引用、运行配置快照。
- Graph/Node 分层结构化日志、来源查询、基础工具授权。
- 可信本地代码运行，元数据日志默认开启。

### 第二阶段：本地多进程与运行能力

- multiprocess 执行、跨进程序列化和 Worker 生命周期。
- 跨进程日志关联、有界队列、大对象制品引用。
- 更完整的工具审批与副作用处理。
- 按配置保存内容、记录驱动测试与重放。
- 在版本约束下逐步加入持久化检查点。

### 后续扩展

- hybrid、auto、远程执行。
- 任意动态多出口、复杂并行循环、子图。
- 命名端口、声明式字段映射、字段级来源追踪。
- 不可信工具隔离、多租户权限和独立审计存储。
- 可视化编辑、运行展示与其他界面。

扩展应继续保持基础使用只需 Graph、Node、Info；增加功能不能迫使简单工作流配置所有高级对象。

## 15. 验收标准

| 方面 | 可验证要求 |
| --- | --- |
| 易用性 | 创建两个节点、声明一次连接、提交 Info 即可获得 Info，无需显式编译或创建运行对象 |
| 所有权 | 跨图连接、重复绑定、未注册目标与不可达节点有明确错误 |
| 单一关系定义 | 修改源节点连接后，关系视图与下一次执行一致；不能独立改写派生矩阵 |
| 信息隔离 | 并行节点无法通过修改共享字典污染对方输入 |
| 来源关联 | 节点生成、原样转发、Graph 结果发布可区分；result.run_id 对应当前运行 |
| 路由 | 未匹配无默认分支时失败；广播与互斥条件路由不会隐式混用 |
| 汇合 | 不组合不同运行或不同分叉组的输入；失败分支不导致永久等待 |
| 结果 | 并行多出口不会按完成时间随意选择一个结果 |
| 执行模式 | 同步与异步调用返回类型固定；不同后端保持定义的依赖与路由语义 |
| 配置 | .env 变更不影响正在运行的配置快照；缺失必要配置在请求外部服务前报告 |
| 日志 | 能从 Graph 通信事件定位目标节点的具体执行和相关 Info；日志缺失不会隐瞒 |
| 安全 | 导出和普通日志中不含密钥；未经授权的框架管理工具不能执行 |
| 副作用 | 超时、取消和重试不被误报为操作未发生或恰好发生一次 |

## 16. 设计取舍与待验证事项

1. 自动注册减少用户操作，但需要严谨处理属性替换、构造失败和注册名称冲突。
2. 源节点声明路由，Graph 派生关系索引，避免节点定义与全局矩阵不一致。
3. 统一 Info 简化接口；强类型必须由明确 Schema 或适配器验证，泛型注解本身不提供运行时保证。
4. 无环顺序图可推断入口与出口；条件、循环和汇合的含义必须显式，不依赖声明先后猜测。
5. 安全默认值会限制默认保存的日志正文，因此完整重放依赖显式内容保存策略。
6. 多进程增加序列化、生命周期和异常处理成本，应在单进程语义稳定后接入同一协议。
7. Node 负责局部声明，Graph 负责全局实施；内部拆分不能变成用户必填的一组基础设施类。

在继续扩展前，优先用三个代表性工作流验证 API：两节点文本处理、带条件回退的审核循环、双分支汇合。观察用户是否能够仅凭 Graph、Node、Info 完成定义、运行和日志定位。
