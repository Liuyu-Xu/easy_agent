## 3. 逐项分析

### S1A-001：共享工具的编辑占用阻断运行释放

关联：A03-002、A03-004。  
位置：[Graph._end_run](../../../easy_agent/graph.py:349)、[Graph._touch_node](../../../easy_agent/graph.py:559)、[definition_locked](../../../easy_agent/_definition.py:24)。

**触发与观察**

Graph A 正在使用内部共享 Tool；Graph B 也引用该 Tool，并进入 edit。在 B 的编辑上下文退出之前，让 A 完成。

A 已记录一次 GraphRunSucceeded，但调用者收到 GraphValidationError；A 的 _active_runs 和 Tool 的 _definition_leases 均留在 1，运行退出后继续修改 A 仍被拒绝。

**根因**

edit 为 Tool 设置 _definition_editor 前，没有拒绝已有运行租约。_end_run 的计数修改又经过 Graph.__setattr__ 上的定义保护；保护发现另一图的 Tool 编辑占用便报错，计数和后续 Tool 释放均被跳过。运行内部资源记账和用户定义修改共用一条拦截路径。

**推荐方案**

- 共享 Tool 的运行租约与编辑占用在同一短临界区原子检查；需要写占用的事务必须先验证没有运行或清理租约，再登记事务。冲突拒绝时不能留下部分占用。
- _end_run 使用专用内部释放路径，在运行取得的资源集合上释放，不重新遍历可变定义，也不进入公开定义修改保护。
- 资源取得与释放有明确的一次性凭据；重复取消、重复清理通知和异常退出均不能重复释放或遗漏释放。
- 运行的成功结果、主异常和资源状态分别维护，释放阶段不得凭空把已成功运行改成定义错误。

**验收要求**

以事件固定“运行先开始、另一图随后编辑、运行完成”的交错；覆盖成功、失败、取消和清理残留。编辑要么在入口完整拒绝，要么采用已定稿的安全隔离方式。真实任务退出后运行计数与租约归零；无成功日志与调用结果冲突。只修 _end_run 的减法不能替代租约冲突检查。

### S1A-002：被拒绝的外部节点污染事务并遭跨图回滚

关联：A03-003、A03-008。  
位置：[Graph._register_node](../../../easy_agent/graph.py:456)、[Graph._restore_definition](../../../easy_agent/graph.py:581)、[Node._bind](../../../easy_agent/node.py:215)。

**触发与观察**

在 A.edit 内尝试把已归属 B 的 Node 注册给 A，捕获 OwnershipError，然后在同一执行上下文合法修改 B.node.prompt。最后让 A 的事务失败。

被拒绝的 B.node 已带有 A 的编辑标记；A 回滚后，B.node.prompt 从合法的新值退回 before。失败注册改变了不属于 A 的对象。

**根因**

_register_node 先 _touch_node，再 _bind；前者记录声明快照并设置编辑标记，后者才检查唯一归属。即使绑定异常被用户捕获，外部 Node 仍留在 A 的事务记录中。回滚随后无条件恢复所有记录对象。

**推荐方案**

- 把所有权、候选资格、重名/替换约束等可拒绝检查置于事务记录和占用之前；预检查不改变对象。
- 事务只记录本图声明、可合法接纳的未绑定候选，以及具有合法共享资格的声明。
- 多对象操作预检查全部对象后再原子登记；单次操作失败且被用户捕获时，不能留下本操作新增的占用。
- 回滚限定在本事务有权管理的声明；不扩大为业务资源或外部动作回滚。

**验收要求**

拒绝注册时外部 Node 的声明、归属和编辑标记均不变；另一图之后的合法修改不会被 A 回滚。补充新注册与 replace_node 两条入口、内部共享 Tool，以及被捕获异常后继续提交的场景。

### S1A-003：全局锁贯穿用户编辑代码，跨图阻塞并存在等待环

关联：A03-003、A03-004。  
位置：[全局 DEFINITION_LOCK](../../../easy_agent/_definition.py:12)、[Graph.edit](../../../easy_agent/graph.py:532)。

**触发与观察**

在 A.edit 内启动线程读取完全独立的 B.to_dict。读线程在 50ms 观察窗口内不能完成；退出 A.edit 后才完成。

这里只实测有限阻塞，没有执行无限等待。若用户在编辑体内等待该线程读完再退出，会形成“A 持锁等线程、线程等 A 释放锁”的等待环。

**根因**

所有 Graph 共用一个 RLock，而 edit 在持锁状态下 yield，把整个用户代码块纳入全局临界区。源码“short-lived lock”的注释不符合实际边界。RLock 的重入身份是线程，不能代替 asyncio task 的事务归属检查。[Python RLock 官方说明](https://docs.python.org/3.10/library/threading.html#rlock-objects)

**推荐方案**

- Graph 自身的快照、提交和运行准入使用短临界区；用户编辑体由显式事务归属保护，不持续占有全局物理锁。
- 共享 Tool 的占用使用资源级短保护；涉及多个资源时采用稳定获取顺序或一次性检查登记，失败时完整撤销。
- 需要验证候选定义时可采用暂存声明和版本核对；不通过深拷贝任意客户端、锁和业务缓存来实现快照。
- 不在物理锁内 await、等待线程、执行用户回调或做可能阻塞的文件读取。保留线程与 task 两种身份检查。
- 不能直接把全局 RLock 换成 asyncio.Lock：项目仍有同步、跨线程入口。

图锁与 Tool 锁的组织属于内部设计建议，应先画清取得、提交、释放顺序，再实施；无需自行新增用户可见的版本或锁 API。

**验收要求**

A 编辑期间，独立 B 能在线程中查询和运行；共享资源消费者受到必要冲突保护。相反资源获取顺序不死锁，同图其他 task 不可编辑。测试使用事件和可释放等待，不靠无限 join 证明死锁。

### S1A-004：删除必要声明后，公共修复入口被保护器堵住

关联：A03-003 的保护边界，兼有既有删除规则不足。  
位置：[Node.__delattr__](../../../easy_agent/node.py:178)、[Graph._tool_declarations](../../../easy_agent/graph.py:355)。

**触发与观察**

del graph.node.tools 成功；之后补回 tools、删除 graph.node，以及 graph.to_dict 均报 AttributeError。

**根因**

Node 允许删除必要声明；新的公共入口保护普遍先遍历 node.tools，假设字段始终存在。因此保护器在修复操作进入前就失败，图只能依靠内部绕过恢复。

**推荐方案**

- 为受管理的必要声明明确删除语义。建议拒绝删除必要字段；若业务需要清空工具，沿用合法赋值 tools=()。
- 可选配置若允许删除，应由正式字段规则定义重置行为；不能自行把所有缺失值都当成空值。
- 保护与验证路径应能诊断缺失声明，并允许受控修复或合法移除受损节点；错误应具有字段与节点信息。
- 读取时容错不等于允许坏定义运行，编译和运行仍需完整校验。

“删除即拒绝”还是“删除即重置”属于需写入字段契约的选择，本轮仅推荐前者。

**验收要求**

必要字段删除被原子拒绝且原值保留；现有正常清空赋值可用。通过受控构造的缺失声明能得到明确诊断，并可按正式规则修复或移除，不再卡在裸 AttributeError。

### S1A-005：按属性名猜测对象角色，破坏 Node 扩展

关联：新增定义保护辅助函数。  
位置：[definition_locked 角色判断](../../../easy_agent/_definition.py:27)。

**触发与观察**

自定义 Node 使用 self._nodes 保存业务缓存。注册后 send_to 和 downstreams 均报 AttributeError。

**根因**

辅助函数以 hasattr(self, "_nodes") 判断对象是否为 Graph，误把该 Node 当成 Graph，随后访问不存在的 _tool_declarations。Node 的业务内部属性被隐式当作框架角色标记。

**推荐方案**

- 用明确类型、各类专用装饰器，或统一的内部定义上下文方法解析所属 Graph。
- 避免为修复循环导入又换用另一个普通属性名猜测类型。
- 声明管理清单与 Node 自定义业务属性分开，不通过禁止一批业务属性名掩盖识别错误。

**验收要求**

带 _nodes 业务属性的 Node 与普通 Node 一样能够连接、查询、编辑和运行；独立 Tool 与归属 Node 的保护规则仍有效。

### S1A-006：停止后漏掉已经完成的其他失败任务

关联：A03-002、协调器资源管理。  
位置：[完成队列与退出清理](../../../easy_agent/graph.py:903)、[清理登记](../../../easy_agent/graph.py:1159)。

**触发与观察**

两个并发分支用同一事件同时释放，并分别抛 ValueError。运行失败退出时，pending_tasks=0，但仍有 1 个已完成任务的异常未被消费。

证据读取 CPython Task 的 _log_traceback 标记；这是审计观察手段，不建议作为生产实现协议。脚本随后主动消费异常，故本次没有以实际打印的告警作为证据。

**根因**

协调器取出第一个失败任务后退出；finally 与清理登记只收集 not task.done() 的任务，队列内其他已完成失败任务既未 result/exception，也未 gather。保存的 [旧执行器片段](../../../tests/evidence/step1/original-runtime.txt) 会 gather 仍在 active 中的任务，其中包括尚未消费的 done 任务；当前筛选丢掉了这一覆盖。

**推荐方案**

- 为每个自有任务保证有明确的结果观察者；退出时消费尚未观察的 done 任务，并继续保有真正未退出的任务。
- 首个运行失败保留为主异常，其他失败作为次要诊断；异常观察与成功提交权限分开，停止后的结果不能重新投递。
- 取消任务单独识别，避免调用 exception() 时抛 CancelledError。
- 覆盖 wrapper 与业务 Task，不能仅观察其中一种。

未消费异常在任务回收时可能产生 “Task exception was never retrieved”，依据 [Python asyncio 官方说明](https://docs.python.org/3/library/asyncio-dev.html#detect-never-retrieved-exceptions)。这是影响推断，不是本次已输出该告警的声明。

**验收要求**

多个分支同时失败、一个失败一个完成、取消与失败竞争均无未观察异常；主异常稳定，次要诊断可查。测试捕获事件循环异常处理器，并在任务释放后验证，无停止后的成功或投递。

### S1A-007：已完成 Task 的保留量随运行长度增长

关联：新加入的 owned_tasks 资源登记。  
位置：[wrapper Task 登记](../../../easy_agent/graph.py:894)、[业务 Task 登记](../../../easy_agent/graph.py:1021)。

**触发与观察**

一个异步节点反馈执行 10 次。在每次提交时，owned_tasks 数量为 2、4、6……20；第 10 次时 20 个 Task 全部已完成。

**根因**

每次尝试分别登记 wrapper 和业务 Task，却没有在结果被消费后移除。Task 的结果、异常和栈帧可能继续引用 Info 或业务对象，导致整次运行期间按总尝试数增长的额外保留。

当前证据证明 Task 引用增长，没有测量 RSS 或泄漏字节数，也不证明运行结束后仍永久泄漏。必要的历史保留应另行按既有历史契约评估。

**推荐方案**

- 区分尚在执行的资源、待消费的完成通知和正式历史。
- wrapper 结果在协调器消费后释放强引用；业务 Task 在其结果已被 wrapper 观察且资源退出后移除。
- 失败和取消路径同样清除已观察的 Task，清理回调只保留必要资源与诊断信息。
- 与 S1A-006 一起设计：不能在读取结果前直接 discard，造成异常丢失或队列引用失效。

Python 官方示例要求运行中的任务有强引用，并在完成后释放；这里还需要按项目完成队列保证先消费再释放。[asyncio Task 引用管理](https://docs.python.org/3.13/library/asyncio-task.html#creating-tasks)

**验收要求**

在长反馈运行中，任务登记量随在途任务和未消费通知变化，不随全部历史尝试线性增长；额外保留的任务均有理由。必要历史保持原契约，异常均被消费，清理租约只在真实退出后释放。

### S1A-008：超时日志失败使停止状态失效

关联：A03-001、A03-002 的新故障路径。  
位置：[超时处理](../../../easy_agent/graph.py:1054)、[停止状态和终态日志](../../../easy_agent/graph.py:1144)。

**触发与观察**

让快分支先形成候选，但暂缓协调器消费；慢分支随后期限到达。仅对该临时 Graph 的 NodeTimedOut 日志写入注入 LoggingError。

- 日志正常的同调度对照：调用者得到 NodeTimeoutError；超时被观察后兄弟成功提交数为 0。
- 注入日志错误：调用者得到 LoggingError；超时被观察后兄弟成功提交数为 1。

脚本以临时子类控制交错和记录观察，保持生产停止与提交代码不变；这是受控日志故障，不是已经发生真实磁盘故障的证据。

**根因**

超时处理先 append NodeTimedOut，再创建超时错误并 _stop_run。日志抛错会跳过停止动作；协调器此时仍见 RUNNING，于是消费先前完成的兄弟候选并记录 NodeSucceeded。

此外，terminal_logged 在实际终态日志成功前被设置为 True，混淆“终态已确定”和“日志已落盘”。即使清理租约覆盖终态日志失败，也不能保护发生在停止动作之前的节点日志失败。

**推荐方案**

- 先确定停止状态、关闭提交和投递、登记实际资源保护，再执行可能失败的节点与图终态日志写入。
- 逻辑终态、资源状态和日志持久化结果分别记录；状态转换幂等，任何日志错误都不能恢复提交资格。
- 日志失败不阻止取消和清理 finally，也不导致继续正常处理完成队列。
- 建议把 NodeTimeoutError 保留为运行主因，将 LoggingError 附为次要诊断；对外异常优先级需在错误契约中明确，本轮不直接改成新公开行为。

**验收要求**

对 NodeTimedOut、NodeCancelled、NodeFailed 和图终态日志分别注入故障，均无停止后的 NodeSucceeded、投递或业务历史成功记录；单一逻辑终态保持稳定，残留任务保护有效，真实退出后资源可释放。验收依据内部状态与实际行为，不把“终态日志不存在”误当作“没有停止”。

## 5. 推荐修改次序及设计依据

1. **先修运行安全边界：S1A-008、001。** 日志失败不能破坏停止，编辑不能阻断资源释放；验证成功、失败与取消出口。
2. **再修事务归属：S1A-002、003。** 明确预检查、取得占用、编辑、提交/回滚、释放的顺序；共享资源冲突必须全有或全无。
3. **处理可修复性和扩展：S1A-004、005。** 先写必要字段删除语义，再修保护器角色解析。
4. **合并处理任务生命周期：S1A-006、007。** 完成通知先消费、异常先观察、资源真实退出后释放引用和租约。
5. **补正式回归和更新验收。** 保留现有 67 项；新用例断言修复后的正确行为，失败注入使用确定性交错。全部通过后再收紧相关 A03 状态。
6. **随后定稿并实现 S1-001—003。** 此前不新增模型闭环、内部工具循环、sequence 或持久化恢复范围。

设计建议继续参考两条已有思路：

- LangGraph 将定义 state、nodes、edges 与 compile 后执行分开。建议本项目加强“可编辑定义—验证计划—单次运行状态”的边界，使正在执行的计划不依赖正在编辑的声明。[LangGraph Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api)
- PyTorch 通过参数、持久/非持久 buffer 等显式注册管理 Module 状态。建议本项目显式列出图定义、共享工具声明、运行资源和业务状态，事务只恢复其有权管理的声明。[PyTorch Module State](https://docs.pytorch.org/docs/main/notes/modules.html#module-state)

上述短锁、事务记录和资源生命周期是结合本项目缺陷提出的设计推断；引用不表示 LangGraph 或 PyTorch 已提供可直接套用的共享 Tool 租约实现。当前 Python 下限为 3.10，也不应未经依赖决策直接用 3.11 才引入的 TaskGroup 替换整个执行器。

下一阶段的门槛应是：跨图编辑不污染、运行退出不漏租约、日志故障不影响停止、所有自有任务结果可观察且资源有界。达成后，再推进尚待定稿的执行与重试能力。
