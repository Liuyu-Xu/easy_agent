# HubNode 设计未决问题与首轮限制

日期：2026-10-17（Asia/Shanghai）  
对应：[修改指导](v0.3-hubnode-modification-guide.md)。2026-10-17后续状态：首轮限定范围已实施并通过最终验收，见 [test1-5报告](test/test1-5-result.md)；下文“现状”保留设计时背景，首轮限制继续有效。

本文件记录尚未完整确定的扩展行为及首轮处理边界。常规实现细节不重复要求用户许可；涉及表中公开行为时，不自行扩大范围。用户已提出的默认隐式汇总广播、显式 HubNode、端口数量／输入键／规则列表、自动生成提示词不在此处重新作为待批准方向。

## HUB-D01：旧 receive 系列接口的迁移

现状：receive、set_receive、clear_receive 仍存在，旧条件／循环路径及历史测试使用它们；简单图当前依赖 receive(all) 才汇合。

首轮方向：新默认路径无需调用 receive；完整直接上游的已有 all 声明如需兼容，应归一化到同一汇合计划，不能另开一个执行器。部分来源声明以及端口绑定冲突明确拒绝或维持旧路径的原支持边界，不能静默忽略。

未决：是否在后续版本整体删除这组公开接口，以及旧条件／循环图的迁移方式。本次指导不授权按“减少函数数量”直接删除仍有用途的接口。若实施需要破坏这些旧行为，先给出具体迁移影响。

## HUB-D02：HubNode 直接作为图入口／出口

现状：run 输入数量按 start 节点数，结果数量按 end 节点数；HubNode 将具有独立的端口数量。

首轮限制：HubNode 仅作为中间节点，拒绝进入 start／end；端口引用也不能放进 start／end。普通 Node 的图边界契约保持。

未决：未来允许单个 Hub 边界时，采用一个包含全部字段的 Info，还是将端口提升为图边界。不得擅自把 input_count／output_count 当成 run 外部列表长度。

## HUB-D03：输出端口广播、重复目标与 Hub 串联

首轮限制：每个显式输入口恰好一条入边、每个显式输出口恰好一条出边，验收以不同普通下游为目标。未知组合在编译时明确拒绝。

未决：一个输出口连接多个目标、同一 Hub 的多个输出口交给同一普通目标，以及多 Hub 串联的完整支持边界。尤其同一目标接收多个端口时，普通“来源节点名”汇总键会冲突；需要明确以端口还是节点作为汇总键，不能覆盖或只保留最后一项。

这不限制普通 Node 的已声明广播，也不禁止一个普通上游明确连接 Hub 的不同输入口；后者必须在内部以端口身份区分接收记录。

## HUB-D04：任意嵌套、条件、循环及动态展开

首轮支持固定简单 DAG 的汇总与分配，每个固定来源本批次提供一次信息；复杂组合应在装配时判定，不留到运行中无限等待。

未决：
- 任意嵌套分叉／汇合的批次嵌套关系；
- 条件未激活来源是否参与 all 等待；
- 条件未激活 end 的结果空位；
- 循环迭代的来源配对；
- 一个端口产生 N 个任务、零任务或同一出口多次产出的收敛协议。

这些问题继续关联 [T13-M02～M05](v0.3-test1-3-issues.md)。不以单个 branch_group 或“增加隐藏节点”宣称已经解决。第一轮不自动展开列表，也不把缺失结果填成 None。

## HUB-D05：端口声明编辑、引用寿命与替换

必须实现：构造时复制列表，运行时冻结，装配失败回滚，不允许外部列表或映射原地修改绕过检查。

首轮保守边界：端口结构变化导致已有引用失效时明确拒绝；节点替换必须检查端口兼容性，不能仅复制节点 ID 和普通边后宣称成功。不支持的编辑应在改变定义前失败，或由现有事务完整恢复。

未决：是否允许空闲时动态增减端口、重命名输入口、调整规则列表长度，以及旧端口引用在替换后的有效性。更新规则内容且数量不变也需要进入同一冻结／回滚机制，不得当作普通可变业务属性处理。

## HUB-D06：更丰富的规则与输出类型

首轮方向：rules 仅接受字符串列表，模型型 Hub 使用固定 out_i 字符串输出；默认隐式枢纽不调用模型。

未决：本地规则型显式 Hub 的 callable 接口、类型化输出、每端口 schema、嵌套字段提取、空值状态对象，以及互斥／完整覆盖分类的确定性约束。

不通过增加 classify、split、transform、dispatch 等多个同义入口提前实现；不从自然语言猜测 JSON schema；不为了兼容任意业务而放宽固定结构校验。

## HUB-D07：结构正确与语义正确的验收边界

端口数量、字段和字符串类型可以由框架严格检查；自然语言分类准确性、事实依据和完整性不能仅靠提示词或 JSON 校验保证。

实施验收必须分别记录结构性回归和业务内容测试。用户数据与系统契约分离有助于降低误用，但不能宣称彻底防止提示注入或模型幻觉。后续如需特定领域准确率，应单独确定样本与指标。

## 本轮记录

最初文档轮次仅建立指导和问题边界，基线见指导第14节。随后用户要求实施并生成test1-5，本轮实现如下保守边界：完整receive(all)归入同一收集路径；Hub仅作中间节点；端口各绑定一次；拒绝Hub串联、同一Hub多口到同一目标及端口关联节点替换；端口结构只读，rules允许同长度修改并受冻结／回滚保护；嵌套多输入汇合继续拒绝。上述扩展问题未因此整体关闭。

## HUB-V01：test1-5 首次真实输出不符

2026-10-17首次联合轮次中，203项确定性测试通过；真实基线单节点通过，一入一出场景在终点固定输出断言处失败，实际共3次请求。证据保留于 [首次轮次](../../../test/evidence/test1-5-common-2026-10-17.json)。未执行后续Hub场景，不算跳过或成功。

运行日志的内容哈希与固定字符串A_OK一致，确认第一业务节点产出该值。旧工具未保存失败时终点正文，仅有哈希和模型事件，因此不能据此唯一归因于模型、提示词或调度。后续已补充先完成凭据检查、再记录有限长度observed_output的验收能力，并保留失败场景模型记录；受控测试覆盖正常不符和含合成密钥的输出，不改业务预期，不放宽断言。

后续成功只能证明对应轮次通过，不能倒推本次失败的唯一根因或将失败记录删除。

第二轮使用修正后的验收工具：204项确定性测试通过，真实请求仍在同一场景停止，实际3次；捕获正文为 `TEST1_\n5_1_1_OK`（此处反斜线n表示实际换行）。其内容哈希与首轮终点哈希一致，确认两次都出现了固定标记内部换行。证据见 [第二轮](../../../test/evidence/test1-5-common-r2-2026-10-17.json)。
