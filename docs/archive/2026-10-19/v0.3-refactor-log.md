# v0.3 代码整修日志：按职责拆分并去除重复实现

日期：2026-10-17（Asia/Shanghai）
范围：只动内部结构，**不改公开 API、不改运行语义**。`Graph`、`Node`、`Tool`、`HubNode`、`Info` 的公开签名与行为保持不变。
约束：每一步改动后立即跑全量确定性回归；任何一步失败即从备份恢复，不带着半成品继续。

---

## 1. 为什么拆

`graph.py` 在整修前是 2702 行、59% 的全库代码，同一个类里混了六类互不相干的职责：注册与所有权、编辑事务、计划编译、调度与执行、路由与汇合、导出与日志。后果不是"文件长"，而是：

- 每个改动的评审范围都是一个 2700 行的文件；
- 编译器与运行时的边界只存在于注释里，`_compile` 与 `_run_plan` 共享 `self` 的 25 个私有字段；
- 同一份"出边声明"被写了三遍（`downstreams`、`relations`、`to_dict` 各一套），改一处要记得改三处。

## 2. 整修后的结构

| 模块 | 行数 | 职责 |
| --- | ---: | --- |
| `graph.py` | **1811**（原 2702，−33%） | 公开 `Graph`：注册、所有权、编辑事务、边界、调度执行、日志入口 |
| `_compiler.py` | 580 | 定义 → 计划的编译与全部计划校验（端口、环、可达、汇合、广播、起点） |
| `_plan.py` | 140 | 计划数据结构（`_Plan`/`_NodePlan`/`_Edge`/`_JoinPlan`/`_ToolDescriptor`）与工具 JSON Schema 构建 |
| `_toolcall.py` | 174 | 模型请求的工具调用：参数校验、执行、结果序列化、事件 |
| `_runtime.py` | 87 | 单次运行状态（`_RunState`/`_WorkItem`/`_Retry`/`_Outcome`/超时信号） |
| 其余 11 个模块 | 1818 | 未改动 |
| **合计** | **4607**（原 4559） | 见 §5 的行数账 |

拆分方式说明：编译器与工具执行采用 **mixin**（`_CompilerMixin`、`_ToolCallMixin`），方法体逐字搬移、`self` 语义不变。这是刻意的保守选择——重写 800 行的 `self.` 引用比搬移更容易引入看不见的错误。数据类与 Schema 构建是纯模块，没有 `self`。

## 3. 真正删掉的重复（不是搬家）

| 位置 | 原状 | 整修后 |
| --- | --- | --- |
| 出边声明 | `Node.downstreams()` 与 `Graph.relations` 各写一套端口/普通/route/route_default 的遍历与命名 | 统一的 `Graph._downstream_specs()`，两处只做投影 |
| `replace_node` 迁移 | 同一段"把 old 换成 new"的规则重写出现 **4 次**（new 节点 ×2、所有来源 ×2） | `_remap_ids` / `_remap_route` / `_remap_receive` 三个纯函数 |
| `_execute_item` 清理 | `state.owned_tasks.discard(business)` 在成功、取消、失败三条路径各写一次 | 单个 `finally`，且只在任务真的结束时移除（被放弃的线程继续被跟踪） |
| 死参数 | `validate_model_config(has_tools=...)` 在工具循环放开后已无任何分支使用 | 删除参数及 `ModelAttempt.has_tools` |
| 死常量 | `Graph._TOOL_ROUNDS_LIMIT`（实际轮次上限在 `_api._MAX_TOOL_ROUNDS`） | 删除 |

净删除重复逻辑约 **110 行**。

## 4. 行为不变性的核对

| 检查 | 结果 |
| --- | --- |
| 确定性回归 3.10.20 | **228 项通过**，exit 0 |
| 确定性回归 3.13.9 | **228 项通过**，exit 0 |
| 联合真实回归 | **passed**，19/19 请求，7 场景全对 |
| PF-1 阻塞探针 | 兄弟分支 0.049s、无期限误判、看门狗 152ms |
| 真实工具探针 | 2 次请求，工具实参 `(2,3)`，输出 `5` |

唯一可观察的差异：`graph.relations` 的**同节点内**条目顺序改为与 `downstreams()` 一致（端口 → 普通 → route）。由于一个节点按校验规则只能声明其中一类（Hub 端口节点不能 `send_to`，route 与 `send_to` 互斥），实际顺序不会变化；测试与真实回归均确认无差异。

## 5. 行数账（诚实版）

| 项 | 行数 |
| --- | ---: |
| 整修前全库 | 4559 |
| 搬进新模块的定义 | ≈846 |
| 新模块的头部、导入与类声明 | ≈75 |

**结论**：全库总量基本持平（+48 行），`graph.py` 减少 891 行。这次整修的价值在结构与可评审性，不在总行数；任何声称"行数腰斩"的说法都不成立。若要继续压总量，下一步应把 `to_dict`/`relations`/`logs` 再抽成 `_export` 模块（约 −160 行），但那是进一步搬家，收益递减。

## 6. 过程中的两次事故（保留记录）

1. **抽取脚本删错区间**：第一次脚本对两组位置分别按原始行号裁剪，第二次裁剪作用在已删除过的列表上，导致 `Graph.__init__` 被切掉一段、文件语法错误。发现方式是立即 `ast.parse`；处理方式是从 `.easy_agent/graph.py.bak` 恢复后修正脚本（合并为一次倒序裁剪）。
2. **漏搬模块级常量**：`_JSON_TYPES` 是赋值语句而非 class/def，脚本只收集定义，导致 `_json_schema` 抛 `NameError`；9 个测试随后失败。加入常量后恢复。

两次事故都没有进入提交状态，因为它们被"每步都跑测试"的流程当场拦下。这也说明：机械搬运必须配可执行的验证，不能只看 diff。
